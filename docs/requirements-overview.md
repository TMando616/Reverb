# 要件定義：Reverb（発信オペレーション基盤）

> **このドキュメントの位置づけ**：Phase 1 の全体像。個別機能の仕様は `.kiro/specs/{feature}/` に分割して詰める。
> **サービス名：Reverb。** 残響＝発信したあとに返ってくるもの、の意。

## 1. 概要

### 1-1. 何を作るか

**「書いたあとに何が起きたか」を記録し続けるための箱。**

Obsidian の断片ノート → 記事ネタ → 執筆 → レビュー → 公開 → **反応の日次追跡** までを1本のパイプラインにする。
Qiita・note・X・ポッドキャストという複数の発信チャネルを、同じ器で横断的に扱う。

### 1-2. なぜ必要か（解く課題）

| 現状の課題 | 本サービスでの解決 |
|---|---|
| ネタが `01_思いつき・日記・メモ` に散らばり、どれが記事になったか分からない | ネタを在庫として状態管理し、公開物まで線でつなぐ |
| 「あの断片メモがこの記事になった」という履歴がどこにも残らない | `contents` が受信箱〜公開まで一貫して状態遷移する |
| Qiita・note・Spotify の数字を各サイトで別々に見るしかない | 全チャネルの指標を1画面に集約する |
| **各プラットフォームは「現在値」しか見せない**（Qiitaは今のLGTM数のみ） | **日次スナップショットを取り続ける**ことで推移を保存する |
| note収益化のリサーチで学んだことを、自分の記事に適用した結果が測れない | タグ別・曜日別・文字数帯別に反応を比較できる |

**4つ目が本質。** 日次でスナップショットを取り続けない限り、「公開後3日で伸びた／じわじわ伸びた」の区別は永久につかない。
これが本サービスが Web アプリである必然性であり、データが構造的に大量になる理由でもある。

### 1-3. 判断基準

迷ったら以下に戻る。

1. 初見の人が README を読んで、何を作ったか理解できるか
2. 4ヶ月で完成するか（未完成の大作より、完成した中規模）
3. 設計判断の理由を自分の言葉で説明できるか
4. 生成AI活用が自然に組み込まれているか（後付けにしない）

## 2. スコープ

### 2-1. Phase 1（2026年9月〜12月・233h）

- ネタの在庫管理（カンバン・状態遷移）
- アプリ内での執筆（Markdown エディタ・リビジョン履歴・セクション編集ロック）
- 企画（シリーズ）単位の共有と、下書きレビュー
- チャネル変換（1本文 → Qiita体裁 / note体裁 / X告知文）
- 公開（Qiita は API 自動、X は Web Intent、note・ポッドキャストは手動補助）
- 日次の指標取得と、公開物の時系列表示
- ダッシュボードと分析
- **MCP サーバー**（手元の Claude Code から操作）

### 2-2. Phase 2 以降

| 項目 | 送る理由 |
|---|---|
| X API による自動投稿・指標取得 | 指標取得は上位プランが必要。Web Intent で代替可能 |
| pgvector による過去記事との重複検出 | あると嬉しいが必須ではない |
| Claude Agent SDK のサーバー組み込み（ブラウザ上でエージェントと対話） | 4ヶ月では手を出さない |
| Instagram 連携 | 画像生成が必要で別プロジェクト規模 |

### 2-3. 対象外（恒久的にやらない）

| 項目 | 理由 |
|---|---|
| note への自動投稿 | 公開 API が存在しない |
| **Obsidian への書き戻し（双方向同期）** | 必ず破綻する。**一方向のみ** |
| ポッドキャスト音声の文字起こし・音声処理 | スコープ外。公開URLと指標だけ扱う |
| **iframe による各プラットフォームの埋め込み** | 各社が `X-Frame-Options: DENY` / CSP `frame-ancestors 'none'` を返す（クリックジャッキング対策）。仮に埋め込めても同一オリジンポリシーで DOM 操作できない |

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| **ネタ / コンテンツ（content）** | 受信箱から公開まで、一貫して状態遷移する単位。記事1本に相当する |
| **企画（project）** | コンテンツをまとめるシリーズ。**共有とロールの単位** |
| **チャネル（channel）** | 発信先プラットフォーム。Qiita / note / X / ポッドキャスト |
| **公開物（publication）** | あるコンテンツを、あるチャネルへ公開した実体。**1コンテンツが複数チャネルに出せる** |
| **指標スナップショット（metric_snapshot）** | ある公開物の、ある日の数値。日次で積み上がる |
| **チャネル変換** | 1つの本文を、チャネルごとの体裁に変換すること |

## 4. アクターとロール

### 4-1. アクター

| アクター | 説明 |
|---|---|
| **オーナー（＝自分）** | 主たる利用者。全操作が可能 |
| **共同編集者（editor）** | 招待されたメンバー。執筆・編集はできるが公開はできない |
| **レビュアー（reviewer）** | 招待されたメンバー。閲覧とコメントのみ |
| **Claude Code** | ローカルで動くエージェント。MCP 経由でサービスを操作する |
| **デモ閲覧者** | デモ用の読み取り専用アカウント |

### 4-2. 権限マトリクス（企画単位）

| 操作 | owner | editor | reviewer | demo |
|---|:---:|:---:|:---:|:---:|
| 企画の閲覧 | ○ | ○ | ○ | ○ |
| メンバー招待・除名 | ○ | × | × | × |
| コンテンツ作成・編集 | ○ | ○ | × | × |
| レビューコメント投稿 | ○ | ○ | ○ | × |
| チャネル変換の実行 | ○ | ○ | × | × |
| **公開・公開取消** | **○** | **×** | **×** | **×** |
| 指標の閲覧 | ○ | ○ | ○ | ○ |

**「3ロール以上」と「共有単位＋リソース単位の権限」の両方を満たす。**

## 5. ユーザーストーリーと受け入れ条件

### E1. ネタの在庫管理

**As a** 発信者
**I want** 思いついたネタを1箇所に溜めて状態を管理したい
**So that** どれが記事になり、どれが眠っているかが分かる

- [ ] ネタを手動で登録できる（タイトル・タグ・メモ）
- [ ] ネタ一覧を状態別のカンバンで表示できる
- [ ] 状態は `受信箱 → 採用 → 執筆中 → レビュー中 → 公開済 → 見送り` の6つ
- [ ] **定義されていない状態遷移は拒否される**（例：受信箱から直接「公開済」へは飛べない）
- [ ] ネタにタグを複数付けられる（多対多）
- [ ] タグ・状態・キーワードで絞り込める
- [ ] 元になった Obsidian ノートのパスを保持できる

### E2. 執筆

**As a** 発信者
**I want** アプリ内で記事を書きたい
**So that** ネタから公開までを1箇所で完結できる

- [ ] Markdown エディタで本文を編集できる（**エディタは既製品を組み込む。自作しない**）
- [ ] 一定間隔で自動保存される
- [ ] **保存のたびにリビジョンが記録される**
- [ ] 過去のリビジョンを一覧・閲覧・復元できる
- [ ] プレビュー表示ができる
- [ ] 文字数がリアルタイムに表示される

### E3. 共同作業とレビュー

**As a** 発信者
**I want** 下書きを他人に見せてコメントをもらいたい
**So that** 公開前に品質を上げられる

- [ ] 企画にメンバーを招待できる（メール or 招待リンク）
- [ ] 招待時に owner / editor / reviewer のいずれかを指定できる
- [ ] **本文の行範囲にアンカーしたコメント**を投稿できる
- [ ] **コメントの投稿・解決が、開いている全員の画面に即座に反映される**
- [ ] コメントを解決済みにできる
- [ ] **同一セクションを2人が同時に編集できない**（セクション単位の編集ロック）
- [ ] ロックの取得・解放が他メンバーの画面に即座に反映される
- [ ] **一定時間操作がないロックは自動解放される**
- [ ] ロック外の箇所を保存する際、**バージョン番号による楽観ロックで競合を検出する**
- [ ] 競合時は差分を提示し、どちらを採用するか選べる

> **【重要】共同編集に Yjs（CRDT）を使わない。** ライブラリが排他制御を全部引き受けてしまい、設計が成果物として残らないため。自前で設計する。

### E4. チャネル変換

**As a** 発信者
**I want** 1つの本文を各プラットフォームの体裁に変換したい
**So that** 書き直す手間なく複数チャネルに出せる

- [ ] チャネルごとの**変換プロファイル**をDBに保持できる（構成ルール・禁則フレーズ・語尾・一人称）
- [ ] 本文とプロファイルから、対象チャネル向けの原稿を生成できる
- [ ] 生成は**非同期ジョブ**として実行され、進捗が画面に出る
- [ ] 生成結果は編集してから公開できる（生成結果をそのまま出さない）
- [ ] X 向けは**280字以内に収まることを検証**し、超過時は警告する
- [ ] タグ候補を提案できる
- [ ] 変換の実行履歴が残る

> 変換プロファイルの初期値は、開発者が既に言語化済みの Qiita／note 書き分けルールを移植する。

### E5. 公開

**As a** 発信者
**I want** 書いたものをできるだけ少ない手数で公開したい
**So that** 公開のたびに面倒な作業をしなくて済む

- [ ] チャネルは `capabilities.publish` として **auto / intent / manual** の3モードを持つ
- [ ] **auto（Qiita）**：ボタン一発で API 経由の投稿ができる。投稿後、URL と外部IDを自動記録する
- [ ] **auto（Qiita）**：公開済み記事の更新（再投稿）ができる
- [ ] **intent（X）**：ボタンを押すと `x.com/intent/post?text=...` が新タブで開き、本文が入った投稿画面が立ち上がる
- [ ] **manual（note / ポッドキャスト）**：ボタンを押すと本文をクリップボードにコピーし、公開画面を新タブで開く
- [ ] manual / intent は、公開後に**URLを貼り戻す**と公開物として登録される
- [ ] 貼られた URL の形式を検証する
- [ ] **公開操作は owner のみ実行できる**
- [ ] 1つのコンテンツを複数チャネルに公開できる（`contents 1 : n publications`）
- [ ] 公開済み一覧から、どのネタがどのチャネルに出たか追える

### E6. 指標の収集

**As a** 発信者
**I want** 公開後の数字が自動で溜まってほしい
**So that** 手を動かさずに推移が残る

- [ ] **1日1回、全チャネルの指標を自動取得する**
- [ ] 取得は**キューを介した非同期ジョブ**として実行される
- [ ] 取得元：Qiita API（LGTM・ストック）、note（公開ページ）、ポッドキャスト（RSS）
- [ ] **ポッドキャストの新エピソードは RSS から自動で公開物として登録される**
- [ ] 取得は公開物ごとに**1日1レコード**として記録される（同日再実行は上書き）
- [ ] **失敗時はリトライされ、リトライ上限に達したらエラーとして記録される**
- [ ] 外部APIのレート制限を超えないよう実行間隔を制御する
- [ ] ジョブの実行状況・エラー履歴を画面で確認できる
- [ ] **手動実行したときは進捗がリアルタイムで画面に流れる**（SSE）
- [ ] 自動取得できない指標（X のインプレッション、Spotify の再生数）は**手動入力できる**

### E7. 分析

**As a** 発信者
**I want** 何が伸びて何が伸びなかったかを知りたい
**So that** 次に書くものを決められる

- [ ] ダッシュボードで全チャネル横断の直近30日を表示できる
- [ ] 伸びている公開物 Top5 を表示できる
- [ ] ネタ在庫のサマリ（状態別の件数）を表示できる
- [ ] 公開物ごとに指標の**日次推移グラフ**を表示できる
- [ ] **公開後 N 日の伸びカーブ**を、公開日の違う記事同士で比較できる（相対日数に正規化）
- [ ] タグ別の反応（平均・中央値）を比較できる
- [ ] 公開曜日別の反応を比較できる
- [ ] 文字数帯別の反応を比較できる
- [ ] 公開月ごとのコホートで累積推移を見られる

### E8. Claude Code 連携（MCP）

**As a** 発信者
**I want** 手元の Claude Code から Obsidian を読ませてサービスに流し込みたい
**So that** ネタ出しから登録までが1コマンドで終わる

- [ ] サービスが **MCP サーバー**としてツールを公開する
- [ ] 公開するツール：`list_ideas` / `create_content` / `update_content` / `search_published` / `get_metrics` / `publish`
- [ ] **MCP サーバーへのアクセスはトークンで認証される**
- [ ] MCP 経由の操作にも、画面と同じ権限チェックが適用される
- [ ] MCP 経由で作られたコンテンツは、作成元が識別できる
- [ ] **サービス側から Obsidian Vault へは一切アクセスしない**（Vault を読むのはローカルの Claude Code の役割）

> **【重要】ブラウザ内ターミナル（xterm.js + node-pty）は採用しない。** 理由は ADR-0007 に記載する。

### E9. 認証・認可

- [ ] メールアドレスとパスワードでログインできる
- [ ] **一般ユーザーの自己登録はできない（招待制）**
- [ ] セッションはトークンで管理される
- [ ] 企画ごとにロールが割り当てられる
- [ ] **権限のない操作はAPI層で拒否される**（画面で隠すだけにしない）
- [ ] 読み取り専用のデモアカウントを用意できる
- [ ] 外部サービスのトークンは**暗号化して保存**される

## 6. 非機能要件

### 6-1. パフォーマンス

| 項目 | 目標 |
|---|---|
| 指標スナップショットの想定件数 | **50万行**（公開物110件 × 365日 × 数年 + テストデータ） |
| ダッシュボード初回表示 | 1秒以内 |
| 分析クエリ（タグ別・コホート） | 2秒以内 |
| 検証方法 | **数十万行をシードして実測し、READMEに Before/After を掲載する** |

> インデックス設計、日次生データと月次ロールアップの持ち分け、パーティショニングの要否を ADR に残す。

### 6-2. セキュリティ

| 項目 | 方針 |
|---|---|
| Qiita アクセストークン | **アプリケーション層で暗号化して保存**。平文保存しない |
| MCP サーバー | トークン認証必須。認可は画面と同一のロジックを通す |
| 一般登録 | **無効（招待制）**。これによりプライバシーポリシーの整備が不要になる |
| Obsidian の取り込み | 対象フォルダを明示的に限定する（日記・気分の記録などの私的な内容を巻き込まない） |
| 公開デプロイ | シェル実行面を持たない（ターミナル埋め込みを採用しない理由の1つ） |

### 6-3. 品質・運用

- [ ] ユニットテスト（Service / Repository 層）
- [ ] 結合テスト（API エンドポイント）
- [ ] GitHub Actions で lint / test / build を実行
- [ ] main マージで AWS へ自動デプロイ
- [ ] OpenAPI による API 仕様の公開
- [ ] **ADR（設計判断の記録）** — 判断の経緯を残す
- [ ] **`.kiro/specs/` をリポジトリに含める**（CC-SDD の実践記録）

## 7. 外部連携仕様

| チャネル | 公開 | 指標取得 | 備考 |
|---|---|---|---|
| **Qiita** | `auto` — API v2 で作成・更新 | `auto` — LGTM / ストック | **唯一フル自動化できる**。トークン管理が必要 |
| **X** | `intent` — Web Intent で投稿画面を開く | `manual` — 手動入力 | **API 不要・OAuth 不要・レート制限なし** |

| **Instagram** | 対象外 | 対象外 | Meta のアプリ審査＋画像の公開URLホストが必要で見合わない |

> **【重要】X と Instagram の API 条件は変更が頻繁。着手時に必ず最新仕様を確認する。**

## 8. データモデル

```
users
  └─ project_members ── projects（企画＝共有単位）
        role: owner / editor / reviewer      │
                                             │
contents（受信箱〜公開まで状態遷移）◄─────────┘
  id, project_id, title, body_md, status, version, source_note_path
  status: 受信箱 → 採用 → 執筆中 → レビュー中 → 公開済 → 見送り
    │
    ├─ content_revisions      保存ごとの履歴
    ├─ content_tags ── tags   多対多
    ├─ review_comments        行アンカー付き・リアルタイム反映
    ├─ section_locks          誰が今どこを編集中か
    │
    └─ publications（公開先チャネルごと）
          id, content_id, channel_id, external_id, url, published_at
            │
            └─ metric_snapshots  ★日次・数十万行
                  publication_id, captured_on, views, likes, stocks, comments

channels                  チャネル定義（publish モード・変換プロファイル）
channel_accounts          外部サービスのトークン（暗号化）
ingest_jobs / job_runs    取得ジョブ・リトライ・エラー履歴
```

**14テーブル。設計の肝は `contents 1 : n publications`。**
「Qiita に書いた記事を、後日ポッドキャストでも話した」を1本のネタとして追える。これがチャネル横断分析の土台になる。

## 10. 技術領域の対応表（抜け漏れ確認）

| 要素 | Phase 1 での担い手 | 対応ストーリー |
|---|---|---|
| **生成AI** | チャネル変換（Qiita ⇄ note ⇄ X 280字）、タグ提案 | E4 |
| **外部API** | Qiita API（投稿＋指標）、note、ポッドキャストRSS | E5 / E6 |
| **認証・認可** | 企画の3ロール ＋「公開は owner のみ」＋ MCP サーバー認証 | E3 / E5 / E8 / E9 |
| **DB設計** | contents ↔ tags 多対多、6状態の遷移、リビジョン履歴、指標スナップショット | E1 / E2 / E6 |
| **パフォーマンス** | 50万行の指標スナップショットに対する集計とインデックス設計 | E7 / §6-1 |
| **リアルタイム** | 編集ロックの取得・解放、レビューコメント、ジョブ進捗（SSE） | E3 / E6 |
| **非同期** | 日次指標取得（キュー・リトライ・レート制限）、LLM変換ジョブ | E4 / E6 |
| **複雑SQL** | 公開後N日の伸びカーブ（ウィンドウ関数）、タグ別・曜日別集計、コホート | E7 |

**すべて「領域を埋めるために足した機能」ではなく、実際に使う機能から自然に出ている。**

## 12. マイルストーン

見積りが上限を超えている以上、作り終えてから「間に合わなかった」では手遅れになる。**中間地点で測り、早くスコープを削る判断をするための区切り。**

組み立ての原則は3つ。

1. **各地点で「縦に1本通っている」こと** — レイヤーごと（DB全部 → API全部 → 画面全部）に作らない。途中で止まったときに動くものが残らないため
2. **削ってはいけないものを先に、削れるものを後に** — 特に**認可は最初に入れる**。後付けが最もつらい
3. **最終月は新しい画面を作らない** — 最後まで機能を足し続けてデプロイとドキュメントが間に合わない、を避ける

### M0 — 2026年9月末 / 58h「土台」

| 内訳 | h |
|---|---|
| 開発環境（Docker Compose）、GitHub Actions で lint / test | 20 |
| 認証（ログイン・トークン） | 12 |
| **企画と project_members、3ロールの認可を API 層に通す** | 13 |
| contents の CRUD と6状態の遷移 | 13 |

**判定：ログインして、企画を作り、ネタを登録して状態を動かせる。**

### M1 — 2026年10月末 / 62h「縦に1本通す」★最重要

| 内訳 | h |
|---|---|
| Markdown エディタ組込・自動保存・リビジョン記録 | 30 |
| タグ（多対多）とカンバン画面 | 10 |
| チャネル変換（まず Qiita 体裁のみ） | 12 |
| Qiita API で公開、URL・外部IDの記録 | 10 |

**判定：ネタを登録し、記事を書き、Qiita に公開できる。この日から自分で使い始める。**

> ここが動かないと、残り2ヶ月の要件がすべて机上のものになる。実際に使い始められれば、以降の要件が当事者の実感から出てくる。

### M2 — 2026年11月末 / 70h「溜めて、見せて、共有する」

| 内訳 | h |
|---|---|
| 指標取得ジョブ（BullMQ・リトライ・レート制限）、SSE 進捗、ポッドキャスト RSS 取り込み | 30 |
| ダッシュボードとウィンドウ関数の分析クエリ | 20 |
| レビューコメント（リアルタイム）、セクション編集ロック、楽観ロック | 20 |

**判定：1週間放置して指標が溜まっている。他人を招待してレビューコメントが即時に届く。**

> **★4ヶ月で最も重い月（70h ＝ 週約17時間）。** 11月中旬時点で遅れていたら、削る順番の1番目（分析画面の統合・−15h）を即発動する。

### M3 — 2026年12月末 / 57h「新しい画面を作らない月」

| 内訳 | h |
|---|---|
| MCP サーバー（既存 API の薄いラッパー。画面を持たない） | 14 |
| X の Web Intent、note の manual アダプタ | 8 |
| AWS デプロイ、デモアカウント | 10 |
| **50万行をシードして性能実測**、README に Before/After 掲載 | 5 |
| 結合テスト・ADR・OpenAPI・README の仕上げ | 20 |

**判定：URL を渡せば初見の人が触れる。README を読めば何を作ったか伝わる。**

### 遅れていた場合の打ち手

| 判定日 | 打ち手 |
|---|---|
| 10月末に Qiita 公開が動いていない | 11月頭に、レビュー機能を「コメントのみ・リアルタイムなし」に格下げする |
| 11月中旬に指標が溜まり始めていない | 削る順番1番目（分析画面の統合）を発動 |
| 11月末にダッシュボードが出ていない | 削る順番3・4番目を発動し、12月は完全にデプロイとドキュメントに充てる |
| 12月中旬にデプロイが終わっていない | **機能追加を全面凍結。** 未完成機能は README に「Phase 2」と明記して切り離す |

> 見積りは実績で 1.3〜1.5 倍に膨らむ前提で見る。**着手前にさらに削るのではなく、M1（10月末）時点の実績時間を測ってから判断する。**
