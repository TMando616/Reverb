# ADR-0013: Python の非同期ジョブ基盤を選定する

- **日付**: 2026-08-29（検討開始）／ 2026-11-03（決定）
- **ステータス**: 採用
- **置き換え対象**: ADR-0011（BullMQ + Redis）
- **関連**: ADR-0017（M1 の変換ジョブを DB キューで回す）、ADR-0006（SSE）、ADR-0009（入り口が3つ）

## 背景

ADR-0011 で BullMQ + Redis を採用したが、**BullMQ は Node.js 専用**のため、
バックエンドを FastAPI に変更した（ADR-0012）時点で成立しなくなった。

ADR-0011 で整理した要件はそのまま有効なので、引き継いで選び直す。

その後 M1 で、変換ジョブを基盤なしの DB キューで動かした（ADR-0017）。
`FOR UPDATE SKIP LOCKED` で拾う・止まった行を回収する・行が状態を持つので落ちても消えない、という骨格はすでに動いている。
**M2 の指標取得ジョブで、これを広げるか、Redis を足して既製の基盤に載せるか**を決める。

## 引き継ぐ要件

| 要件 | 理由 |
|---|---|
| リトライ・バックオフ | 外部 API（Qiita・RSS）は落ちる。日次指標取得が1回の失敗で欠測になってはいけない |
| ジョブ履歴の永続化 | `job_runs` テーブルで実行結果を追える必要がある |
| 手動再実行 | 画面から失敗ジョブを叩き直せること |
| レート制限 | 外部 API の制限に合わせて流量を絞る |
| ローカルと本番で同じ構成 | docker compose でそのまま動くこと |
| 進捗の通知 | SSE でジョブ進捗を流す（ADR-0006） |

加えて、M2 では**1日1回の定期実行**が要る（E6）。

### 規模

公開物は Phase 1 で約110件。指標取得は1日1回なので、**1日あたり数百件のジョブ**にしかならない。
秒間スループットや低遅延が要る場面は無い。

## 選択肢

| 候補 | 利点 | 欠点 |
|---|---|---|
| **自前の DB キュー（ADR-0017 を広げる）** | 追加のミドルウェアが無い。M1 で動いている仕組みをそのまま使える。リトライ・スケジュール・レート制限を**自分で設計した成果物**として残せる | 書く量が増える。定期実行・バックオフを自分で正しく作る必要がある |
| **Postgres をキューにするライブラリ**（procrastinate 等） | Redis なしでリトライ・定期実行が手に入る | 実績・情報が少ない。現行仕様を確かめる手間がかかる。設計を引き受けてしまう |
| **Celery + Redis** | Python の事実上の標準。情報量が最大。リトライ・スケジュール（Celery Beat）が揃う | 重い。asyncio との相性が悪く、FastAPI の async ハンドラと世界が分かれる |
| **ARQ + Redis** | asyncio ネイティブ。軽量で読みやすい | ジョブ履歴・管理 UI が薄く、`job_runs` は自前で持つ必要がある |
| **Dramatiq + Redis** | ミドルウェア機構が素直。リトライ・レート制限が組み込み | asyncio サポートが後付け。日本語情報が少ない |
| **Taskiq + Redis** | asyncio ネイティブで FastAPI の `Depends` をそのまま使える。設計が新しい | 新しく、実績が少ない |

## 決定

**Redis を入れない。PostgreSQL をキューにした自前のワーカーを、ADR-0017 から広げて M2 の指標取得にも使う。**

- 指標取得用に **`job_runs`** を作る。`conversion_jobs` には統合せず、**変換専用のまま残す**（変換ジョブは原稿・保留中の結果を持つので、汎用の行に寄せると意味が薄まる）。共通にするのは「拾い方」（`SKIP LOCKED` で拾う・止まった行の回収）だけにする
- **リトライ**：`job_runs` に試行回数と次に実行してよい時刻を持たせ、失敗したら指数バックオフで時刻をずらして `queued` に戻す。上限に達したら `failed` で確定し、エラーを残す
- **定期実行**：常駐ワーカーが一定間隔で「今日の分」を投入する。**`(ジョブの種類, 対象日)` のユニーク制約**で、プロセスが複数あっても二重に投入されない
- **手動再実行**：画面から同じ種類のジョブを1行投入する（失敗した行は書き換えずに残す）
- **レート制限**：チャネルごとに同時実行を1本に絞り、呼び出しの間隔をあける。数百件／日なので、これで外部 API の制限を超えない
- **進捗（SSE）**：`job_runs` の状態を正とする。SSE への伝え方（Postgres の `LISTEN/NOTIFY` か、DB のポーリングか）は `metrics` の design.md で決める

具体的なカラム・間隔・上限回数は `metrics` スペックの design.md で決める。

## 理由

- **`job_runs` を自前で持つ前提なので、既製の基盤から得るものが少ない。** 検討時点で「履歴は自前で持つ」と決めていた（判断の観点に書いていた）。そうなると基盤に任せられるのはリトライと定期実行くらいで、この規模では Redis と依存を1つずつ増やすほどの価値がない
- **M1 の骨格がもう動いている。** `SKIP LOCKED` での取得・止まった行の回収・行が状態を持つことは、変換ジョブで検証済み。足すのはリトライの時刻管理と定期投入で、どちらも DB の制約で正しさを担保できる
- **設計そのものが成果物になる。** リトライ・冪等な定期実行・レート制限を自分で設計することは、Yjs を使わずに編集ロックを設計する（ADR-0004）のと同じ軸。ライブラリに任せると、この領域の設計が成果物として残らない
- **Service の呼び方が変わらない。** ワーカーは今と同じく Service を呼び、commit をワーカー側が持つ。ADR-0009 の「入り口が3つ」を壊さない
- **本番の構成が増えない。** AWS の構成（ADR-0003）は未決で、Redis を入れるとマネージドサービスかコンテナが1つ増える。PostgreSQL だけで済めば、コストも運用も減る

### 却下した案

- **Celery**：asyncio と世界が分かれ、async で書いた Service をそのまま呼べない。Redis も増える
- **ARQ / Dramatiq / Taskiq**：どれも Redis が要る。`job_runs` を自前で持つ以上、Redis を足して得られるのはリトライと定期実行だけで、この規模では見合わない。Taskiq は ADR-0013 の評価軸（asyncio ネイティブ・`Depends` の再利用）には一番合っていたが、上の理由は変わらない
- **Postgres ベースのライブラリ**：Redis 不要という点では同じだが、実績が少なく仕様を確かめるコストがかかる。M1 の仕組みがすでにあるので、新しい依存を入れるより広げる方が早い

## 影響

- **ADR-0017 の「M2 で `app/jobs/worker.py` を基盤に書き直す」は不要になる。** 変換ワーカーはそのまま残す。`JobDispatcher` ポート（M2 でキューに積む実装に替える予定だったもの）は、何もしない実装のままでよい
- docker compose・本番に Redis を足さない。requirements-overview の構成図・技術スタックの「Redis」を外す
- ワーカーは当面 FastAPI と同じプロセス（lifespan で起動する asyncio タスク）で動かす。`SKIP LOCKED` とユニーク制約で、プロセスを増やしても・別コンテナに出しても正しく動く
- **覆す条件**：ジョブ数が桁違いに増える、秒単位の遅延が問題になる、などの場合。そのときはキューの取得と投入をワーカー側に閉じているので、Service と画面は変えずに基盤へ移せる
