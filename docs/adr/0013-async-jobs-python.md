# ADR-0013: Python の非同期ジョブ基盤を選定する

- **日付**: 2026-08-29
- **ステータス**: 検討中
- **置き換え対象**: ADR-0011（BullMQ + Redis）

## 背景

ADR-0011 で BullMQ + Redis を採用したが、**BullMQ は Node.js 専用**のため、
バックエンドを FastAPI に変更した（ADR-0012）時点で成立しなくなった。

ADR-0011 で整理した要件はそのまま有効なので、引き継いで選び直す。

## 引き継ぐ要件

| 要件 | 理由 |
|---|---|
| リトライ・バックオフ | 外部 API（Qiita・RSS）は落ちる。日次指標取得が1回の失敗で欠測になってはいけない |
| ジョブ履歴の永続化 | `job_runs` テーブルで実行結果を追える必要がある |
| 手動再実行 | 画面から失敗ジョブを叩き直せること |
| レート制限 | 外部 API の制限に合わせて流量を絞る |
| ローカルと本番で同じ構成 | docker compose でそのまま動くこと |
| 進捗の通知 | SSE でジョブ進捗を流す（ADR-0006） |

## 選択肢

| 候補 | 利点 | 欠点 |
|---|---|---|
| **Celery + Redis** | Python の事実上の標準。情報量が最大。リトライ・スケジュール（Celery Beat）が揃う | 重い。asyncio との相性が悪く、FastAPI の async ハンドラと世界が分かれる |
| **ARQ** | asyncio ネイティブ。Redis のみで動く。軽量で読みやすい | ジョブ履歴・管理 UI が薄く、`job_runs` は自前で持つ必要がある |
| **Dramatiq** | ミドルウェア機構が素直。リトライ・レート制限が組み込み | asyncio サポートが後付け。日本語情報が少ない |
| **Taskiq** | asyncio ネイティブで FastAPI の `Depends` をそのまま使える。設計が新しい | 新しく、実績が少ない |

## 決定

**未決。M2（2026年11月・指標取得ジョブの実装）着手前までに決める。**

## 判断に使う観点（先に書いておく）

- **`job_runs` を自前で持つ前提に立つ**なら、ジョブ基盤側の履歴機能は評価軸から外れ、asyncio ネイティブかどうかが主軸になる
- FastAPI の `Depends` で組んだ Service を**ジョブからも同じ形で呼べるか**（ADR-0009 の「入り口が3つ」を壊さないこと）
- **知名度ではなく本プロジェクトの要件で選ぶ。** 選定理由は必ずこの ADR に書き切る
