# ADR-0009: レイヤー構成と依存方向

- **日付**: 2026-08-26
- **ステータス**: 採用

> **2026-08-29 追記（ADR-0012）：依存方向の原則は変更なし。** 実装が NestJS から FastAPI に変わったため、
> DI は FastAPI の `Depends` で組む。フレームワークが層を強制しないので、層をまたぐ import は
> `import-linter` の契約チェックで CI に検出させる。

## 背景

このアプリには**入り口が3つある。**

| 入り口 | 実体 |
|---|---|
| ブラウザ | HTTP Controller |
| Claude Code | MCP サーバー |
| 日次バッチ | ジョブワーカー（→ ADR-0013） |

3つが同じデータを同じルールで操作する。ルールをどこに置くかを決める必要がある。

## 選択肢

1. **レイヤードアーキテクチャ**（Controller → Service → Repository、一方向）
2. Controller に業務ロジックを直接書く（薄いレイヤーなし）
3. 双方向の参照を許す

## 決定

**`Controller → Service → Repository → DB` の一方向依存とする。下位が上位を参照することは禁止。**

補足ルール：

- チャネルアダプタは Service から呼ぶ。Controller から直接呼ばない
- ジョブのプロセッサは Service を呼ぶ。Repository を直接叩かない
- **MCP サーバーは Service 層を経由する。専用の抜け道を作らない**
- **Service は Request / Response を知らない。** `@Req()` を Service まで持ち込まない

## 理由

### 1. 入り口が増えても業務ルールが1箇所で済む ★このプロジェクトでは最重要

業務ルールが Service にあれば、3つの入り口すべてが同じ Service を通るのでルールは1回書けば済む。

逆にルールを Controller に置くと、こうなる。

> **「公開は owner のみ」を Controller に書いた場合**
> → MCP の `publish` ツールから公開されたとき、そのチェックが通らない
> → **認可が二重実装になり、必ずズレる。ズレた瞬間にセキュリティホール**

状態遷移の検証（受信箱から直接「公開済」へは飛べない）も同じ理由で Service に置く。

### 2. 変更の波及が止まる

| 変更の種類 | どこで止まるか |
|---|---|
| DBのカラム追加、ORM の差し替え | **Repository** |
| リクエスト形式・認証ヘッダの変更 | **Controller** |

Service は業務ルールだけを持つので、両側の都合から独立する。
ORM を未決（ADR-0002）のまま設計を進められるのは、この構造による。

### 3. テストの単位が決まる

Service のテストは Repository をモックにすれば書ける。
Repository が Service を呼んでいたら循環してモックできない。

### 4. 循環参照を構造的に禁止できる

双方向を許すと `A → B → A` が生まれ、DIコンテナが解決できなくなる。
Python では遅延 import で回避できてしまうが、**これが出てきたら設計が壊れているサイン**として扱う。

## 各層の責務

| 層 | やること | やらないこと |
|---|---|---|
| **Controller** | DTOの検証、認証済みユーザーの取り出し、ステータスコードの決定 | **業務判断をゼロにする** |
| **Service** | 業務ルール、状態遷移の妥当性、認可判断、トランザクション境界、複数Repositoryの協調 | HTTPを知らない |
| **Repository** | 永続化とクエリの組み立て | **業務判断を持たない** |

## 想定される崩れ方（レビュー時のチェック項目）

| 崩れ方 | 何が起きるか |
|---|---|
| Controller に「ownerかどうか」を書く | **MCP経由でチェックが漏れる** |
| Repository に「公開済みは除外する」を書く | 業務ルールが下層に染み出し、別のユースケースで再利用できなくなる |
| **Service が Request オブジェクトを受け取る** | **HTTPに依存してジョブから呼べなくなる**（最も起きやすい） |

## 影響

- 単純な CRUD でも、何もしない Service を1枚挟むことになる。**一貫性のためにこのコストは受け入れる**（例外を作ると、どこに何があるか読めなくなる）
- MCP サーバーの実装は既存 Service の薄いラッパーになる。これが「MCPサーバーは15h」という見積りの根拠でもある
