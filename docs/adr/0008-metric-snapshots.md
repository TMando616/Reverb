# ADR-0008: 指標スナップショットのテーブル設計と性能

- **日付**: 2026-11-03
- **ステータス**: 採用
- **関連**: `.kiro/specs/metrics/design.md` §3-2・§9・§15-1、requirements-overview §6-1

## 背景

公開物ごとの指標（閲覧数・いいね・ストック・コメント・再生数など）を、**1日1回のスナップショット**として取り続ける。
各プラットフォームは現在値しか返さないので、推移はこのテーブルにしか残らない。

想定は **50万行**（公開物110件 × 365日 × 数年 ＋ テストデータ）。この上で、ダッシュボードを1秒以内、分析（タグ別・コホート）を2秒以内に返す（requirements-overview §6-1）。

チャネルによって取れる指標が違う（Qiita は LGTM・ストック、ポッドキャストは再生数だけ、など）。
決めるのは次の3つ。

1. 指標を列で持つか（横持ち）、指標名と値の行で持つか（縦持ち）
2. 何を主キーにし、どのインデックスを張るか
3. 月次のロールアップやパーティションを最初から用意するか

## 選択肢

### 持ち方

| 案 | 利点 | 欠点 |
|---|---|---|
| **横持ち**（`views` / `likes` / `stocks` / `comments` の列。取れない指標は NULL） | 1日1行。推移・増分（`lag()`）・集計で行を組み替えなくてよい。行数が最小 | 指標の種類を増やすと列を足すマイグレーションが要る |
| 縦持ち（`metric_name`, `value`） | 指標の種類を増やしても列が増えない | 行数が指標の数だけ増える（4倍）。どの集計でも行を列に組み替える必要があり、SQL が読みにくく遅くなる |
| JSONB に指標をまとめる | 柔軟 | 集計のたびに取り出しと型変換が要る。CHECK 制約（負の値の禁止）を張りにくい |

### ロールアップ・パーティション

| 案 | 利点 | 欠点 |
|---|---|---|
| 最初から月次のロールアップ（マテリアライズドビュー）を持つ | コホートなど月単位の集計が軽くなる | リフレッシュの運用と、生データとの食い違いを持つことになる。必要か分からないうちに作る |
| 年ごとのパーティション | 古いデータを切り離せる | 50万行は PostgreSQL にとって小さく、効果が出る規模ではない。主キーにパーティションキーを含める制約が増える |
| **何も作らず、インデックスだけで始める** | 単純。必要になったら足せる | M3 の実測で目標を外したら手を入れる必要がある |

## 決定

**横持ち・公開物×日付の主キー・ロールアップとパーティションは作らない（M3 の実測まで）。**

```
metric_snapshots
  publication_id  bigint      ─┐ PK
  captured_on     date        ─┘ （JST の日付）
  project_id      bigint      公開物から写す（非正規化）
  channel         text        公開物から写す（非正規化）
  source          text        auto / manual（行単位）
  views / likes / stocks / comments   bigint NULL, CHECK (>= 0)
  captured_at     timestamptz
  updated_by      bigint NULL
```

- **PK `(publication_id, captured_on)`**：「公開物×日で1行」を DB で保証する。同じ日の再取得は `INSERT ... ON CONFLICT DO UPDATE` で上書きする。公開物1件の推移はこの PK の範囲検索で引ける
- **インデックス `(project_id, captured_on)`**：ダッシュボードの「企画×直近30日」
- **`project_id` / `channel` を非正規化して持つ**：ダッシュボードの集計を `publications` と JOIN せずに済ませる。公開物の企画・チャネルは作成後に変わらないので、ずれない。整合は複合 FK `(publication_id, project_id) → publications(id, project_id)` で守る
- **指標の意味（`views` が閲覧数か再生数かインプレッションか）は、チャネルの capabilities（コード）に置く。** テーブルは汎用の4列だけ
- **`source` は行単位。** チャネルの指標は「全部自動」か「全部手入力」のどちらかなので、値ごとに持たない
- **欠測は行が無い状態で表し、0 で埋めない**

## 理由

- **1日1行にすることで、分析 SQL が素直になる。** 日次の増分は `lag()` 1つで出せる。縦持ちだと、増分を出す前に指標ごとに行を組み替える必要がある
- **指標の種類は Phase 1 の4チャネルで出そろっている。** 4列で全チャネルが収まり、列を足す場面はチャネルを足すときくらい。チャネルを足すときはどのみちアダプタのコードが要る（ADR-0005）
- **測る前に最適化しない。** 50万行・1日数百行の追加なら、適切なインデックスがあれば集計は十分速いと見込んでいる。ロールアップは「生データと食い違わないか」という新しい問題を持ち込むので、必要と分かってから足す。requirements-overview §12「測ってから判断する」と同じ考え方

### 却下した案

- **縦持ち**：行数が4倍になり、どの集計でも組み替えが要る。柔軟さが活きるのは指標の種類が頻繁に増える場合で、このプロダクトはそうではない
- **JSONB**：集計で取り出しと型変換が毎回要り、負の値を CHECK で止めにくい
- **最初からロールアップ・パーティション**：効果が出る規模ではなく、運用の手間だけが先に増える

## 影響

- 指標の種類を増やすには列を足すマイグレーションが要る
- **M3 で50万行をシードして実測する**（metrics design.md §15-1）。目標（ダッシュボード 1秒・分析 2秒）を外したら、月次のマテリアライズドビューを足して測り直し、結果をこの ADR に追記する。Before/After は README に載せる
- 手入力と自動取得を同じ指標で混ぜられない。混ぜたくなったら、値ごとの `source` か別テーブルが必要になる
