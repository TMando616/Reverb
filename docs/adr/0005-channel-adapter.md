# ADR-0005: 外部公開を3モードのアダプタで抽象化する

- **日付**: 2026-08-26
- **ステータス**: 採用

## 背景

Qiita・note・X・ポッドキャスト・Instagram へ公開したい。
ところが**プラットフォームごとに API の事情がまったく違う。**

### 調査結果

| プラットフォーム | 公開API | 指標取得 | 備考 |
|---|---|---|---|
| **Qiita** | **あり**（API v2 で作成・更新） | あり（LGTM・ストック） | 唯一フル自動化できる |
| **X** | あり（上位プランが必要な部分あり） | **上位プランが必要** | 投稿だけなら Web Intent で代替可能 |
| **note** | **なし** | 公開ページから一部のみ | 公開APIが存在しない |
| **ポッドキャスト** | **なし**（Spotify for Creators で手動） | RSS から新エピソードを取得可能 | |
| **Instagram** | あり（Graph API） | あり | **Meta のアプリ審査＋画像の公開URLホストが必要**で見合わない |

### iframe による埋め込みは原理的に不可能

「各サービスの投稿画面を iframe で埋め込んで、そこから投稿すればよいのでは」という案を検討したが、**技術的に不可能**だった。

1. **各社がフレーム表示を拒否している。** `X-Frame-Options: DENY` / CSP `frame-ancestors 'none'` を返す。クリックジャッキング（透明な iframe を重ねて意図しない操作をさせる攻撃）対策として標準的な措置
2. **仮に埋め込めても操作できない。** 同一オリジンポリシーにより、親ページから iframe 内の DOM には一切触れられない。本文の流し込みも投稿ボタンの押下もできない

→ **「表示はできるが操作はできない」ため、埋め込む意味がない。**

## 選択肢

1. 対応できるチャネルだけ実装し、他は諦める
2. チャネルごとに個別の実装を書き、UI側で分岐する
3. **アダプタで抽象化し、能力の違いをフラグで表現する**

## 決定

**`ChannelAdapter` インターフェースを定義し、`capabilities.publish` で3モードを表現する。**

| モード | 対象 | 挙動 |
|---|---|---|
| `auto` | Qiita | API 経由で投稿・更新まで完全自動 |
| `intent` | X | **Web Intent** で本文入りの投稿画面を開く。ユーザーはポストを押すだけ |
| `manual` | note / ポッドキャスト | 整形済み本文をクリップボードにコピー＋公開画面を新タブで開く → 公開後に URL を貼り戻す |

```ts
interface ChannelAdapter {
  readonly capabilities: {
    publish: 'auto' | 'intent' | 'manual'
    metrics: 'auto' | 'manual' | 'none'
    format: 'markdown' | 'text'
    maxLength?: number          // X なら 280
  }
  publish(content): Promise<PublicationRef>
  fetchMetrics(ref): Promise<Metrics>
}
```

## 理由

### 1. 各社の事情を UI とジョブから隔離できる

モードのフラグを見れば挙動が決まるので、**分岐が1箇所に収まる。**
「Qiita なら〜、note なら〜」という条件分岐が画面やジョブに散らばらない。

### 2. チャネル追加がアダプタ追加だけで済む

Phase 2 で X の API 連携に切り替える場合も、アダプタの `capabilities.publish` を `intent` から `auto` に変えるだけで、呼び出し側は変更不要。

### 3. 自動化できないチャネルでも体感を自動に近づけられる

`manual` でも「コピー＋公開画面を開く」を標準動作にすることで、手順が5アクションから2アクションになる。
**完全自動でなくても、実運用としては十分に回る。**

### 4. Web Intent の採用でコストが大きく下がった

X について、当初は API 連携（OAuth 2.0 PKCE の実装）を想定していた。
Web Intent なら **API キー・OAuth・レート制限のすべてが不要**で、URL を組み立てるだけで済む。

副次的な効果として、**DB にトークンを保管する対象が Qiita だけ**になり、暗号化して扱う秘密情報が1つ減った。

## 影響

- **`intent` と `manual` は「公開後に URL を貼り戻す」導線が必須。** これを忘れると公開物として登録されず、指標も取得されない
- 貼られた URL の形式検証が必要
- **X と Instagram の API 条件は変更が頻繁。実装時に必ず最新仕様を確認すること**
- Instagram は対象外とする。将来対応するなら画像生成が前提になり、別スコープになる
- チャネルアダプタは Service から呼ぶ。Controller から直接呼ばない（ADR-0009）
