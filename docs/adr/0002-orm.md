# ADR-0002: ORM に SQLAlchemy 2.0 を採用する

- **日付**: 2026-08-30
- **ステータス**: 採用

## 背景

`foundation` スペックの `design.md` に入る前に、ORM を確定させる必要がある。
データモデル（`requirements-overview` §8、14テーブル）を定義し、マイグレーションを回し、
Repository 層の実装方針を決めるのに ORM の選定が前提になる。

ADR-0012 でバックエンドを FastAPI に変更したため、候補は Prisma / TypeORM から
**SQLAlchemy 2.0 / SQLModel / Tortoise ORM** に差し替わっている（ADR-0012 §影響）。

このプロジェクトの要件のうち、ORM の選定軸を決めるのは次の4つ。

1. **複雑SQL（E7）** — 公開後 N 日の伸びカーブ（ウィンドウ関数）、タグ別・曜日別集計、
   公開月コホート。50万行の `metric_snapshots` に対して 2 秒以内（tech.md 非機能）
2. **レイヤー構成（ADR-0009）** — 永続化の知識を Repository に閉じ込め、
   Service は ORM セッションを知らない状態を保つ。`models.py` と `schemas.py` を分ける（structure.md）
3. **非同期** — FastAPI の async、非同期ジョブ基盤（ADR-0013）の両方から同じ Repository を呼ぶ
4. **楽観ロック** — `content.version` による競合検出（`foundation` F6 / F7、ADR-0004）

マイグレーションは tech.md で **Alembic に確定済み。**

## 選択肢

| 案 | 利点 | 欠点 |
|---|---|---|
| **A. SQLAlchemy 2.0**（async・ORM ＋ Core 併用） | Core で SQL をほぼそのまま組み立てられ、分析クエリの逃げ道になる。Data Mapper + Unit of Work で永続化を Repository に閉じ込めやすい。Alembic が同じ作者・同じメタデータで一級。`version_id_col` で楽観ロックが標準機能。2.0 は `Mapped[]` で mypy と整合 | 冗長。セッション／Unit of Work の管理は自分で組む。学習コストが高い |
| B. SQLModel | Pydantic と SQLAlchemy モデルを1クラスに統合でき、ボイラープレートが減る。FastAPI と同じ作者 | **`models.py` / `schemas.py` を分ける structure.md と逆行する。** 非同期のサポートが薄い。0.x で破壊的変更が続く。複雑SQLでは結局 SQLAlchemy Core の知識が要る＝二重の学習 |
| C. Tortoise ORM | 最初から async ネイティブ。Django ライクで API が簡潔。学習が速い | **ActiveRecord 寄り**（`await obj.save()`）で層の境界が溶ける。マイグレーションが Aerich で **Alembic 指定と食い違う。** ウィンドウ関数など分析SQLが弱く生SQLに落ちがち。mypy サポートが弱い。エコシステムが小さい |

## 決定

**SQLAlchemy 2.0 を採用する。**

- エンジンは **asyncio 拡張**（`create_async_engine` / `AsyncSession`）
- ドメインのテーブルは **ORM（Declarative + `Mapped[]`）** でマッピングする
- E7 の分析クエリは **Core（`select()`）** で書き、必要なら `text()` で生SQLに落とす。ORM と同じ接続・トランザクションで併用する
- マイグレーションは **Alembic**（SQLAlchemy のメタデータを autogenerate の元にする）
- 楽観ロックは `mapper` の **`version_id_col`** を使う

## 理由

### 1. 複雑SQL に逃げ道が要る — ここで候補が絞れる

E7 はウィンドウ関数・コホート・50万行集計で、tech.md が 2 秒以内を要求している。
**SQLAlchemy Core は SQL の構造をそのまま式で組み立てられ**、ORM と同じ `AsyncSession` の中で併用できる。
ORM で書ける部分は ORM、重い分析は Core、逃げ切れなければ `text()`、という三段構えが1つのライブラリで完結する。

- **Tortoise はこの層が弱い。** ウィンドウ関数やコホートは生SQL文字列に落ちやすく、
  そのとき型も接続管理もライブラリの外に出る
- **SQLModel は結局 SQLAlchemy Core に降りる。** なら最初から Core を持っている SQLAlchemy でよい

### 2. 永続化を Repository に閉じ込められる — ADR-0009 と噛み合う

SQLAlchemy は **Data Mapper + Unit of Work**。「モデルが自分を保存する」ActiveRecord ではない。
`AsyncSession` を Repository の中だけで扱い、Service にはドメインオブジェクトで返す設計が自然に組める。

Tortoise の `await content.save()` は、モデルインスタンスが永続化の責務を持つ。
これは ADR-0009 の「Repository に業務判断を持ち込まない／Service は DB を知らない」という境界を溶かす方向に働く。

`.importlinter` に **「`modules.*.service` から `sqlalchemy` を import してはいけない」** という契約を追加でき、
層の分離を CI で担保できる（ADR-0012 §影響の「仕組みで守る」と同じ発想）。

### 3. `models.py` と `schemas.py` を分ける前提と整合する

structure.md は ORM モデル（`models.py`）と Pydantic（`schemas.py`）を別ファイルに分けている。
リクエスト／レスポンスの形と、テーブルの形は、ライフサイクルも変更理由も違うためだ。

**SQLModel の中心的な売りは、この2つを1クラスに統合すること。** 意図的に分けている構造と正面から反する。
ADR-0004（Yjs 却下）・ADR-0012（Django 却下）と同じ軸で、
**「設計判断を引き受けてしまうこと」を、このプロジェクトでは利点として数えない。**

### 4. マイグレーションが Alembic 一択で、齟齬がない

tech.md は Alembic を指定済み。Alembic は SQLAlchemy と同じ作者で、
SQLAlchemy のメタデータをそのまま autogenerate の入力にできる。
Tortoise を選ぶと Aerich になり、確定済みの標準と食い違う。

### 5. 楽観ロックがフレームワーク機能で入る

`foundation` F6 / F7 の「古い `version` を指定した更新は 409」は、
SQLAlchemy の `version_id_col` を設定すれば **UPDATE 時のバージョン照合とインクリメントが自動**で入る。
自前でカウンタと WHERE 条件を書かなくてよい。ADR-0004 の楽観ロック方針の実装土台になる。

### 6. 型 — 2.0 を選ぶ理由そのもの

SQLAlchemy 2.0 は `Mapped[]` アノテーションで API を作り直し、mypy と整合するようになった。
tech.md の開発標準（`mypy` を CI で回す）と合う。1.x を避け 2.0 系に限定するのはこのため。

## 影響

### 実装方針に課される制約

- **Repository だけが `AsyncSession` と `sqlalchemy` に触れる。** Service には触らせない（`.importlinter` で契約化）
- Repository は ORM モデルを外に出さず、ドメインオブジェクト（dataclass もしくは Pydantic）に詰め替えて返す
  ※ 詰め替えのコストと、モデルを漏らす代償のどちらを取るかは `foundation` design.md で最終判断する
- セッションのライフサイクル：HTTP は FastAPI の `Depends` で request スコープ。
  ジョブ側は `async with async_session() as session:` を自前で管理する
- E7 の分析は Core の `select()` で書く。ADR-0008（指標テーブル設計）はこの前提で書く
- Alembic の autogenerate は差分の下書きに留め、生成されたマイグレーションは必ず目視する

### 却下した案を後で選び直すとしたら

- **SQLModel**：`models.py` / `schemas.py` の分離をやめ、テーブルと API 契約を一体で扱う方針に転換する場合。
  ただしその判断は structure.md の変更を伴う
- **Tortoise**：E7 の分析要件が単純な集計だけに縮小し、かつ非同期ジョブ（ADR-0013）もやめる場合。
  そのとき Tortoise の簡潔さと async ネイティブが利点として立ち上がる

### 他 ADR への影響

| ADR | 扱い |
|---|---|
| ADR-0008（指標テーブル設計・性能） | 未着手。分析は Core / 生SQL で書く前提で起こす |
| ADR-0009（レイヤー構成） | 変更なし。`sqlalchemy` の import を Repository に限る契約を `.importlinter` に足す |
| ADR-0013（非同期ジョブ基盤） | 変更なし。ジョブから Repository を呼ぶ際のセッション管理を選定時に考慮する |
