# ADR-0015: フロントのスタイリングとデータフェッチ層

- **日付**: 2026-09-27
- **ステータス**: 採用

## 背景

`frontend.md` §7 に「M0 で決める」として2つ残っていた。M0 の画面（`design.md` §12-2 の4画面）に
着手する前に確定させる必要がある。

- スタイリング：Tailwind CSS / CSS Modules
- データフェッチ層：TanStack Query 等の採用可否。**条件は `frontend.md` §2 の状態3分類を満たせること**

前提として、フロントは M0 では最小画面だが、M2 のダッシュボードまで**同じ流儀で押し通せること**を
求める。作り直しが全画面に波及するため。

## 選択肢

### スタイリング

| 案 | 利点 | 欠点 |
|---|---|---|
| **A. Tailwind CSS** | 既製の非スタイル部品（Radix 等）と組み合わせやすく、`components/ui/`（`frontend.md` §5）を自作する量が減る。デザイントークンを CSS 変数の1箇所に集約できる | 追加依存が増える。クラス文字列の重複を畳む方針を別に決める必要がある |
| B. CSS Modules | Next.js に標準で入っていて追加依存ゼロ。コンポーネント単位で閉じる | `ui/` の部品とトークンの仕組みを自分で設計・実装することになる |

### データフェッチ層

| 案 | M0 での実装 | 問題 |
|---|---|---|
| A. M0 では採用しない | Server Component の `fetch` のみ | content-pipeline で導入するとき、その時点の Client Component を書き換える |
| B. M0 から TanStack Query を入れる | 一覧を Client Component + `useQuery` に寄せる | **採用条件を検証できないまま流儀が固まる** |
| **C. M0 では採用せず、検証タスク付きで判断を持ち越す** | A と同じ | ほぼ無い（決定の先送りに期限が付く） |

## 決定

**スタイリングは Tailwind CSS を採用する。**

**データフェッチ層は M0 では採用しない。** 判断は `content-pipeline` スペックの設計時に、
**編集ロックのプッシュ（WebSocket）をフェッチのキャッシュへ反映する検証と併せて**行う。
その検証タスクを `content-pipeline` の `tasks.md` の先頭に置く。

M0 の一覧はサーバー状態として Server Component で BFF から取得し、更新後の再取得は Next.js の
仕組みで行う（具体的な API は `frontend/node_modules/next/dist/docs/` を見て確定する。記憶で書かない）。

## 理由

### Tailwind を選ぶ理由

1. **`components/ui/` を自作する量が減る。** ボタン・ダイアログ・ドロップダウンのキーボード操作と
   アクセシビリティを自前で面倒を見る形にしたくない。非スタイルの部品に見た目を付ける組み合わせが取れる
2. **デザイントークンを1箇所に置ける。** M2 のダッシュボードで色・余白・タイポグラフィを画面をまたいで
   揃える必要が出る。後から変えるときに触る場所が1つで済む
3. **このプロジェクトの成果物はバックエンドの設計**（ADR-0004 / ADR-0009）。フロントは部品が揃っている
   側に寄せ、自作の総量を減らす

CSS Modules を却下する理由は「追加依存ゼロ」と引き換えに `ui/` とトークンの仕組みを自作することになり、
上の3点と逆方向に働くため。

### データフェッチ層を M0 で決めない理由

採用条件は `frontend.md` §2 の3分類、特に**プッシュ由来のサーバー状態をフェッチと同じキャッシュに
流し込めること**。ADR-0004 で Yjs を捨てたため、「誰がどこを編集中か」の整合は自前で取る。

**M0 にはプッシュ由来の状態が無い**（`design.md` §12-2）。つまり条件を満たせるかを確かめる材料が
この時点に存在しない。ここで選ぶと、検証せずに決めたものが全画面の流儀になる。

B を却下する理由も同じ。M0 の4画面は小さいので、あとで Client Component を書き換える量（A / C の欠点）は、
検証しないまま流儀を固めるリスクより小さい。

A ではなく C にするのは、**「いつ何を確かめて決めるか」を残さないと未決のまま忘れる**ため。

## 影響

- `frontend.md` §7 の2項目を消し、決定を §2 / §5 側に反映する
- **M0 の一覧は Server Component で取る。** Client Component の中でフェッチを始めない（`frontend.md` §3）
- `content-pipeline` の `tasks.md` に「ロックのプッシュをキャッシュへ反映する検証」を最初のタスクとして置く。
  ここでデータフェッチ層の採否を決め、必要なら ADR を1本足す
- Tailwind のバージョンと設定の作法（v4 で設定が CSS 側に寄った）は、`frontend/` を作ったあとに
  実際に入ったバージョンのドキュメントで確定する。**記憶で書かない**（CLAUDE.md）
- `components/ui/` に使う部品ライブラリ（Radix 等）は 8.4 で画面を作るときに決める。ここでは決めない

## 覆すとしたら

Tailwind を捨てるのは、デザインを一から自分で設計する方針に変えた場合。全画面のクラスに触ることになる。

データフェッチ層は、上記の検証で「プッシュをキャッシュに流し込めない」と分かった場合に、
自前の薄いキャッシュを設計する方向へ倒れる。その判断も ADR に残す。
