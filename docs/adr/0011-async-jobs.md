# ADR-0011: 非同期処理基盤に BullMQ + Redis を使う

- **日付**: 2026-08-26
- **ステータス**: 採用

## 背景

以下の2種類の遅い処理がある。

| 処理 | 性質 |
|---|---|
| 日次の指標取得（Qiita / note / ポッドキャストRSS） | **外部APIに依存し、必ず失敗する日がある** |
| チャネル変換（LLM 呼び出し） | 数秒〜数十秒かかる |

とくに前者は、レート制限・タイムアウト・先方の仕様変更で落ちる。

## 選択肢

| 候補 | 評価 |
|---|---|
| **BullMQ + Redis** | リトライ・バックオフ・ジョブ履歴・手動再実行が揃う。ローカルでも同じ構成で動く |
| `node-cron` + 素の関数 | 最も軽い。**ただし失敗が握り潰されて消える** |
| AWS EventBridge + Lambda | マネージドで運用は楽。**インフラが複雑になり、ローカル開発が面倒** |

## 決定

**BullMQ + Redis を採用する。**

## 理由

### 日次取得は「失敗する前提」の処理だから

必要なのは実行そのものではなく、**失敗の扱い**である。

- リトライとバックオフ
- 失敗の記録（いつ・どのチャネルで・何回目で諦めたか）
- 手動での再実行

`node-cron` + 素の関数だと、**失敗が消えて「昨日の数字が取れていない」ことに気づけない。**
指標の時系列が欠けると、公開後N日の伸びカーブ（複雑SQLの中心）が成立しなくなる。

### レート制限の制御が必要だから

外部APIごとに実行間隔を制御する必要がある。キューがあれば同時実行数と間隔を宣言的に指定できる。

### ローカルと本番で同じ構成にしたいから

EventBridge + Lambda はローカルで再現しにくい。
Redis なら docker compose に1行足すだけで、開発と本番の差分が小さくなる。

## 影響

- **Redis が必須コンポーネントになる。** インフラ構成（ADR-0003）とコスト見積りに含める
- ジョブの実行状況とエラー履歴を保存するテーブル（`ingest_jobs` / `job_runs`）が必要
- 進捗の可視化は SSE で行う（ADR-0006）
- Repository を直接叩かず Service を経由する（ADR-0009）
