# ADR-0006: WebSocket と SSE の使い分け

- **日付**: 2026-08-26
- **ステータス**: 採用

## 背景

リアルタイム性が必要な箇所が3つある。

| 用途 | 通信の向き |
|---|---|
| ジョブ進捗の表示 | サーバー → クライアント |
| 編集ロックの取得・解放 | 双方向 |
| レビューコメントの反映 | 双方向 |

すべてを1つの方式に寄せるか、用途ごとに分けるかを決める必要がある。

## 選択肢

| 方式 | 特徴 |
|---|---|
| **ポーリング** | 実装が最も簡単。遅延とリクエスト数がトレードオフ |
| **SSE** | サーバー → クライアントの一方向。HTTPそのまま。**再接続が標準で入っている**。プロキシを通りやすい |
| **WebSocket** | 双方向。接続管理・再接続・ハートビートを自前で持つ必要がある |

## 決定

**双方向が必要かどうか、だけで判断する。**

| 用途 | 方式 |
|---|---|
| ジョブ進捗の表示 | **SSE** |
| 編集ロックの取得・解放 | **WebSocket** |
| レビューコメントの反映 | **WebSocket** |

## 理由

### ジョブ進捗に WebSocket は過剰

進捗はサーバーから流すだけで、クライアントから送るものがない。
SSE は HTTP のままなので**ブラウザ側の再接続が標準で入っており**、プロキシやロードバランサも素通しできる。
ここで WebSocket を使うと、**接続管理・再接続・ハートビートを自前で持つコストだけが乗る。**

### 編集ロックとコメントは双方向が必要

- ロック要求：クライアント → サーバー
- ロック解放の通知：サーバー → 他のクライアント
- コメント投稿：クライアント → サーバー
- コメント反映：サーバー → 他のクライアント

SSE で受けて POST で送る構成も可能だが、**接続が2本になり、順序と生存確認が扱いにくくなる。**

### ポーリングを採用しない理由

編集ロックは「他人が今どこを触っているか」を示すもので、遅延がそのまま体験の悪さになる。
ジョブ進捗も、数秒ごとのポーリングだと「動いているのか止まっているのか」が分からない。

## 影響

- 通信方式が2つ混在する。**どちらを使うかの判断基準を明文化しておく必要がある**（本ADRがそれ）
- WebSocket 側は接続管理を自前で持つ。切断時にロックを解放する処理が必要になる
- ロックのタイムアウトによる自動解放は、WebSocket の切断検知だけに頼らず**サーバー側の時刻でも判定する**（切断を取りこぼしてもロックが残り続けないようにするため）
