# ADR-0014: 認証トークンの保持場所と API 呼び出し経路

- **日付**: 2026-08-29
- **ステータス**: 採用

## 背景

ADR-0010 でフロントエンド（Next.js）と API（FastAPI）を分離したが、影響の欄に次の1行を残したまま、
実装方針を決めていなかった。

> 認証はトークンをフロントで保持し、リクエストに付与する形になる

**「フロントで保持」の中身が未定。** ここを決めないと M0 の認証（12h）に着手できない。

このアプリの事情として、以下を満たす必要がある。

| 要件 | 出典 |
|---|---|
| メール＋パスワードでログイン。セッションはトークンで管理 | E9 |
| **権限のない操作は API 層で拒否する。画面で隠すだけにしない** | E9 / tech.md |
| 読み取り専用のデモアカウントを公開 URL で触れるようにする | E9 / M3 |
| MCP サーバーはトークン認証で、**画面と同一の認可ロジックを通る** | ADR-0007 / ADR-0009 |
| Markdown 本文・レビューコメント・外部から取り込んだ記事本文を画面に描画する | E2 / E3 / E6 |

最後の1行が効く。**このアプリは他人が書いた Markdown を描画する面を常時持つ**ため、
XSS の攻撃面が構造的に広い。トークンの置き場所はこれを前提に決める必要がある。

## 選択肢

| 案 | トークンの置き場所 | 経路 |
|---|---|---|
| A | `localStorage` | ブラウザ → FastAPI を直接 |
| B | httpOnly Cookie（FastAPI が発行） | ブラウザ → FastAPI を直接（クロスオリジン） |
| **C** | **httpOnly Cookie（Next.js が発行）** | **ブラウザ → Next.js（BFF）→ FastAPI** |

### A を却下する理由

`localStorage` は JavaScript から読める。**XSS が1つ通った時点でトークンが持ち出される。**
上記のとおり本アプリは Markdown 描画面を常時持つため、「XSS は起きない」を前提に置けない。

### B を却下する理由

httpOnly にできるので A よりは良いが、フロントと API がオリジンをまたぐため次が付いてくる。

- Cookie に `SameSite=None; Secure` が必要 → **CSRF 対策を別途実装する必要がある**
- ブラウザ側のサードパーティ Cookie 制限の影響を受け得る。**将来ブラウザ側の都合で壊れる**
- CORS を `credentials` 込みで開ける必要があり、許可オリジンの管理が増える

**セキュリティの都合でブラウザ仕様に依存する設計になる**のが受け入れられない。

## 決定

**C を採用する。**

1. **セッショントークンは httpOnly / Secure / SameSite=Lax の Cookie に置く。** JavaScript から読めない
2. **Cookie は Next.js と同一オリジンで発行する。** ブラウザは FastAPI を直接叩かない
3. **Next.js のサーバー側が Cookie からトークンを取り出し、`Authorization` ヘッダに載せ替えて FastAPI に中継する**

```
                  Cookie (httpOnly)         Authorization: Bearer
ブラウザ ──────────────────► Next.js ────────────────────────► FastAPI
                            （BFF：中継のみ）                  ├─ Service 層で認可
                                                               │
Claude Code ───────────────────────────────────────────────────┘
                  Authorization: Bearer（MCP トークン）
```

### BFF の責務は「中継」だけ — ADR-0010 との関係

**これは「Next.js に API を持たせる」ことではない。** ADR-0010 の決定は維持する。

| Next.js（BFF）がやること | やらないこと |
|---|---|
| Cookie ⇄ `Authorization` ヘッダの載せ替え | **業務ロジック** |
| 未ログイン時のリダイレクト | **認可の判断** |
| FastAPI のレスポンスをそのまま返す | データの加工・集約 |

**判定基準：Next.js 側のコードが `contents` や `publications` の業務ルールを知り始めたら、それは越境。**
認可は例外なく FastAPI の Service 層で判定する（ADR-0009）。
BFF は「誰のリクエストか」を伝えるだけで、「何をしてよいか」は一切判断しない。

### MCP は BFF を通らない

Claude Code は `Authorization: Bearer <MCP トークン>` で **FastAPI を直接叩く**（ADR-0007）。
ブラウザではないので Cookie も XSS も関係なく、BFF を挟む理由がない。

**経路は2つに分かれるが、認可は Service 層の1箇所に合流する。** これが ADR-0009 の要求そのもの。

### WebSocket / SSE の扱い

リアルタイム（ADR-0006）は BFF でプロキシしない。
**短命の接続チケットを BFF 経由で取得し、それを使って FastAPI に直接接続する。**

- WebSocket を Next.js で中継すると、接続の生存管理が二重になる
- チケットは1回限り・数十秒で失効させ、URL に載っても実害が出ない状態にする

※ 具体的な実装は **M2（リアルタイム着手時）に検証してから確定する。** ここでは方針のみ。

## 理由

1. **JavaScript から読めるトークンがブラウザ上に一切存在しない。** XSS が通ってもセッションを持ち出せない
2. **同一オリジンなので `SameSite=Lax` が使える。** CSRF 対策とサードパーティ Cookie 問題が同時に消える
3. **CORS が不要になる**（ブラウザは FastAPI を直接叩かない）
4. **デモアカウントも同じ経路に乗る。** 公開 URL 用に別系統を作らない
5. **API 側は「Bearer トークンを受け取る」1通りだけを実装すればよい。** ブラウザ用と MCP 用で認証方式を分岐させない

## 影響

- **ADR-0010 の影響欄「CORS の設定が必要になる」は不要になる。** ブラウザからの直接アクセス面が無くなるため
- ホップが1つ増える。Next.js のサーバー側が落ちると画面は死ぬ（API と MCP は生きる）
- **BFF の中継コードが業務ロジックを持ち始めていないか**、レビューで毎回見る必要がある。ここが崩れると ADR-0010 が実質的に無効化される
- ログアウトは Cookie の削除とサーバー側トークンの失効の両方が要る
- **具体的な Next.js 16 の API（Cookie の読み書き、サーバー側でのリクエスト転送の作法）は、
  `frontend/node_modules/next/dist/docs/` を参照して M0 で確定する。記憶で書かない**

## 覆すとしたら

Next.js を捨てて SPA + CDN 配信に変える場合。その時は B（httpOnly Cookie + CSRF 対策）に寄せることになる。
A（`localStorage`）に戻す選択肢は、Markdown 描画面がある限り無い。
