# ADR-0001: バックエンドフレームワークに NestJS を採用する

- **日付**: 2026-08-26
- **ステータス**: 採用

## 背景

バックエンドを TypeScript で書くにあたり、フレームワークを選ぶ必要がある。
制約は2つ。

- **4ヶ月・247h（見込み）で完成させる。** 言語やフレームワークの習得に時間を使いすぎると本体が終わらない
- **1人で4ヶ月書き続ける。** 途中で構造が崩れると、後半の速度が落ちる

## 選択肢

| 候補 | 利点 | 欠点 |
|---|---|---|
| **NestJS** | DIコンテナ・モジュール分割・デコレータ・ORM併用の構成。構造が強制される | ボイラープレートが多い |
| Express + 自前構成 | 軽い。自由度が高い | **構造の型がない。DIがなくテストのたびに手作業でモックを組む** |
| Fastify | 高速 | 構造の問題は Express と同じ |
| Hono | 軽量・モダン | 構造の型がない。規模が大きくなると効いてくる |
| tRPC | 型安全性が最大 | **外部から叩かれる入り口（MCPサーバー）を持つため、REST + OpenAPI のほうが素直** |

## 決定

**NestJS を採用する。**

## 理由

### 1. 既存の設計経験がそのまま移植できる

PHP/Laravel でのバックエンド実務があり、NestJS は Laravel とほぼ同型の構成を持つ。

| Laravel | NestJS |
|---|---|
| サービスコンテナ | DI コンテナ |
| サービスプロバイダ | Module |
| ミドルウェア | Guard / Interceptor |
| FormRequest | DTO + ValidationPipe |
| Eloquent | Prisma / TypeORM |

**未経験なのは「言語」であって「バックエンドの設計」ではない。**
この差分の小ささにより、4ヶ月を言語習得ではなくアプリの質に投資できる。

### 2. フレームワークが構造を強制する

1人開発では、これが最も効く。Express は自由すぎて、4ヶ月かけると構造が崩れる。
NestJS は Module / Provider / Controller の型が決まっているため、**後から読んでも構造が追える状態が保たれる。**

### 3. DI があるのでテストが書ける

Service のテストで Repository をモックに差し替えられる。テストが要件に入っている以上、ここは外せない。

## 影響

- **ボイラープレートのコストを受け入れる。** 単純な CRUD でも Module / Controller / Service / Repository を書く。小規模なら明らかにオーバーキルだが、テーブル14・モジュール6の規模では見合う
- 依存方向のルール（ADR-0009）は、NestJS の DI を前提に成立する
- tRPC を捨てたので、フロントとの型共有は OpenAPI からの生成で担保する必要がある
