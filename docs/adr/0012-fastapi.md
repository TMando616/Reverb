# ADR-0012: バックエンドフレームワークを NestJS から FastAPI に変更する

- **日付**: 2026-08-29
- **ステータス**: 採用
- **置き換え対象**: ADR-0001（NestJS）

## 背景

ADR-0001 で NestJS を採用したが、その後 ADR-0004 〜 ADR-0011 で設計を詰めた結果、
**このアプリが必要とするものが、ADR-0001 の時点で見えていたものと変わった。**

具体的には、以下の3つが後から確定した。

1. **MCP サーバーをサービス側に実装する**（ADR-0007）
2. **Claude API による下書き変換をジョブとして走らせる**（ADR-0011）
3. **50万行の指標スナップショットを分析する**（tech.md 非機能要件）

いずれも ADR-0001 の「選択肢」の表には存在しなかった要件で、
**フレームワークの選定軸そのものを変える。**

加えて ADR-0001 は、tRPC を却下した影響として次の宿題を残していた。

> tRPC を捨てたので、フロントとの型共有は OpenAPI からの生成で担保する必要がある

これは NestJS では「別途デコレータで組む作業」として残り続ける。

**まだコードを1行も書いていない（M0 未着手）ため、切り替えコストが実質ゼロの唯一のタイミングでもある。**

## 選択肢

| 案 | 利点 | 欠点 |
|---|---|---|
| **A. FastAPI に変更する** | OpenAPI が標準装備。MCP / Claude API の公式 SDK が Python で最も厚い。Pydantic で境界のバリデーションが型と一体になる | 層構造がフレームワークに強制されない。ADR を数本書き直す |
| B. NestJS のまま進める | ADR・steering の書き直しが不要。構造が強制される | OpenAPI・MCP・LLM のいずれもエコシステムが薄い側に賭けることになる |
| C. Django に変更する | 認証・ORM・管理画面が最初から揃う。完成は最も早い | **バックエンド設計を自分で組む余地が減る。** 本プロジェクトの目的と噛み合わない（→ 理由4） |

## 決定

**バックエンドを FastAPI（Python）に変更する。フロントエンドは Next.js 16 のまま変更しない。**

## 理由

### 1. アプリの中核が Python 側のエコシステムに寄っている

| 要件 | 事情 |
|---|---|
| MCP サーバー（ADR-0007） | 公式 SDK（`mcp`）が一級。**仕様策定元の言語**であり、追随が最も早い |
| Claude API による変換（ADR-0011） | 公式 SDK（`anthropic`）は Python が最も成熟している |
| 50万行の指標分析 | 重い集計を SQL から押し出す必要が出たとき、Python 側に逃がせる |

3つのうち2つは**このアプリの差別化要素そのもの**（ADR-0007 でブラウザ内ターミナルを捨ててまで MCP を選んでいる）。
そこで薄いほうのエコシステムを選ぶ理由がない。

### 2. ADR-0001 が残した「OpenAPI の宿題」が構造的に解ける

FastAPI は Pydantic のスキーマから **OpenAPI を自動生成する。**
tech.md の開発標準「API 仕様は OpenAPI で公開」が、**作業ではなく初期状態**になる。

フロントの型は生成された OpenAPI から起こすため、tRPC を捨てたことによる型安全性の穴が、
NestJS より少ない手数で埋まる。

### 3. 外部チャネルの境界でバリデーションが型と一体になる

チャネルアダプタ（ADR-0005）は Qiita API・RSS・note から**信用できない外部データ**を受け取る。
Pydantic はバリデーションと型定義が同一の宣言になるため、
「境界で検証し、内側では検証済みの型しか流れない」を**構造として担保できる。**

`intent` / `manual` モードのようにチャネルごとに形が違うレスポンスを扱う以上、ここは効く。

### 4. 設計を自分で組む余地を残す — ADR-0004 と同じ判断軸

本プロジェクトの目的は **「バックエンドの設計を成果物として残すこと」**。
ADR-0004 で Yjs（CRDT）を却下したのは、ライブラリが排他制御を全部引き受けてしまい、
設計が成果物として残らないためだった。**同じ軸をフレームワーク選定にも適用する。**

- **Django を却下**：認証・ORM・管理画面を最初から与えてしまい、設計する対象が消える
- **NestJS の「構造が強制される」は、この目的では利点として数えない**

層をどう切り、依存をどう注入し、契約をどう検証するかを自分で決めて ADR に残すほうが、目的に適う。

## 影響

### 失うもの：フレームワークによる構造の強制

ADR-0001 の理由2「フレームワークが構造を強制する」は **FastAPI では成立しない。**
NestJS の Module / Provider / Controller に相当する型がなく、`Controller → Service → Repository`（ADR-0009）は
**規約として自分で守る必要がある。**

理由4のとおりこれは意図した選択だが、**「気をつける」で守ると必ず崩れる。** 仕組みで担保する。

- ディレクトリ構造で層を物理的に分ける（structure.md）
- 依存の注入は FastAPI の `Depends` に寄せ、Service を Router で直接 import して組み立てない
- **層をまたぐ import を CI で検出する。** `import-linter` の契約を置き、違反はテストと同じ扱いでビルドを落とす

3つ目が本命。**これが無いと ADR-0009 は絵に描いた餅になる。** M0 の CI 構築に含める。

### 差し替えが必要な決定

| ADR | 扱い |
|---|---|
| ADR-0001（NestJS） | **置き換え済み**（本 ADR） |
| ADR-0002（ORM 選定） | 対象を Prisma / TypeORM から **SQLAlchemy 2.0 / SQLModel / Tortoise ORM** に差し替え。未着手のまま |
| ADR-0011（BullMQ + Redis） | **BullMQ は Node 専用のため成立しない。** 置き換え済みとし、要件を引き継いで ADR-0013 で選び直す |
| ADR-0009（レイヤー構成） | 依存方向の原則は不変。DI の記述のみ FastAPI の `Depends` に読み替え |
| ADR-0005 / 0006 / 0007 / 0010 | **影響なし。** 判断の中身が言語に依存していない |

### 覆すとしたら

MCP または LLM 連携をスコープから外し、かつフロントとの型共有を tRPC に戻す場合。
その時は ADR-0001 の論理がそのまま復活する。
