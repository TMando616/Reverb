# ADR-0004: 共同編集に CRDT（Yjs）を使わない

- **日付**: 2026-08-26
- **ステータス**: 採用

## 背景

企画に招待した共同編集者（editor）が、同じ記事を編集しうる。
競合をどう扱うかを決める必要がある。

実際の利用形態は以下を想定している。

- 1つの企画のメンバーは**数人**（招待制。一般登録は無効）
- 同時に同じ記事を開くことはあるが、**同じ段落を同時に打ち続ける状況は稀**
- レビュアーはコメントのみで、本文を編集しない

## 選択肢

| 候補 | 利点 | 欠点 |
|---|---|---|
| **Yjs（CRDT）** | 文字単位の同時編集が破綻しない。実績が豊富 | **排他制御をライブラリが全部引き受ける**。状態が肥大する。永続化・awareness・競合UIが別途必要 |
| OT（Operational Transformation） | 同上の体験を実現できる | 自前実装は難度が高すぎる |
| **セクション単位の編集ロック ＋ 楽観ロック** | 競合の発生自体を防ぐ。設計を自分で決められる | 同一セクションの同時編集はできない |
| 何もしない（Last Write Wins） | 実装ゼロ | **書いた内容が黙って消える。** レビュー中の記事で起きたら致命的 |

## 決定

**セクション単位の編集ロック ＋ バージョン番号による楽観ロックを自前で実装する。**

- **セクションロック**：見出し単位で取得・解放。**タイムアウトによる自動解放**あり
- **楽観ロック**：保存時にバージョン番号を照合し、競合を検出
- **競合時**：差分を提示し、どちらを採用するか選ばせる（黙って上書きしない）

## 理由

### 1. 排他制御の設計を自分で持ちたい

CRDT を入れると競合解決はライブラリの内部で完結し、**設計判断が成果物として残らない。**
ロックの粒度・解放条件・競合時のUXを自分で決めることに、このプロジェクトでは意味がある。

### 2. 想定する利用形態に対して CRDT は過剰

同時編集者が数人で、同一段落の同時入力が稀なら、**競合を「解決する」より「起こさない」ほうが素直。**

### 3. リビジョン履歴と二重管理になる

本サービスは**保存ごとに `content_revisions` へ履歴を残す**設計になっている。
CRDT は独自の更新履歴を内部に持つため、両方を保存すると同じものを二重に管理することになる。

### 4. スコープに収まらない

Yjs を入れると、永続化（y-websocket + persistence）・awareness・競合UIなど別セットの作業が発生する。
247h の見積りには収まらない。

## 影響

- **同一セクションの同時編集は仕様として拒否する。** 「他の人が編集中です」を明示する
- ロックの粒度を決める必要がある（見出し単位を想定）
- **ロックの解放漏れ対策が必須。** WebSocket の切断検知だけに頼らず、サーバー側の時刻でもタイムアウト判定する（ADR-0006）
- オフライン編集はサポートしない
- ロック制御は Service 層に閉じる。**将来 CRDT に置き換える判断をしたときに、影響範囲を Service 内に留めるため**
