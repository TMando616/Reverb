# Reverb 技術選定 解説 — なぜこのスタックなのか

**「何を選んだか」ではなく「なぜ選べたか」を、判断の前提から順に説明するドキュメント。**

---

## 0. このドキュメントについて

### 何のための文書か

Reverb は技術選定を `docs/adr/`（ADR = Architecture Decision Record）に1件ずつ残している。
ADR は「その1つの判断」を深く掘るので、全部読むと**選定同士のつながり**が見えにくい。

この文書は逆で、**個々の判断を浅く広く、1本のストーリーとしてつなぐ**。
「バックエンドを一度 NestJS に決めてから FastAPI に覆した」「ORM で SQLAlchemy を選んだ」
「CRDT ライブラリを使わない」——これらが**同じ1つの判断軸から出ている**ことを示すのが狙い。

### 想定する読者

- バックエンド開発の経験はあるが、**Python / FastAPI / SQLAlchemy は初めて**という人
- Laravel（PHP）または Spring Boot（Java）の経験がある人には、対応する概念を随時示す

### 前提：Reverb とはどんなアプリか

**「書いたあとに何が起きたか」を記録し続けるための箱。**

Qiita（技術記事）、note（エッセイ）、X、ポッドキャストという複数の発信チャネルを持つ人が、
「ネタを思いつく → 記事を書く → レビューする → 公開する → その後どれだけ読まれたか」までを
1本の線でつなぐアプリ。

特徴的なのは最後の部分で、**各プラットフォームは「今の数字」しか見せてくれない**。
「公開3日後に伸びたのか、じわじわ伸びたのか」を知るには、毎日その数字を記録し続けるしかない。
だから日次でスナップショットを取り続ける。これが Web アプリとして作る必然性であり、
**データが構造的に大量になる**理由でもある（指標スナップショットは50万行を想定）。

## 1. 選定の前提 — Reverb が抱える4つの制約

技術を選ぶ前に、「このアプリが何を要求しているか」を4つに整理する。
以降の選定はすべて、この4つのどれかに紐づいている。

### 制約1：入り口が3つある

同じデータ（ネタ・記事・公開先・指標）を、**3つの経路**が操作する。

| 入り口 | 実体 | 例 |
|---|---|---|
| ブラウザ | HTTP API | 画面からネタを登録する |
| Claude Code | MCP サーバー | ローカルのエージェントが `create_content` を呼ぶ |
| 日次バッチ | ジョブワーカー | 毎日 Qiita の閲覧数を取りに行く |

3つが**同じ業務ルール**（「公開できるのは owner だけ」「受信箱から直接『公開済』へは飛べない」）を
通らなければならない。ルールを置く場所を1箇所に決めないと、3回書くことになり、必ずズレる。
ズレた瞬間にセキュリティホールになる。→ **レイヤードアーキテクチャ（第6章）** の動機。

### 制約2：4ヶ月で完成させる

2026年9〜12月の個人開発。見積りは上限を超えている。
**言語やフレームワークの習得に時間を溶かすと本体が終わらない。**
「未完成の大作」より「完成した中規模」を選ぶ。→ 最初に **NestJS** を選んだ動機（第4章）。

### 制約3：バックエンドの設計そのものが成果物

Reverb はポートフォリオを兼ねる。「動くアプリ」だけでなく
**「層をどう切り、依存をどう注入し、競合をどう解決したかを自分の言葉で説明できること」**が価値。

ここから、独特の判断が出てくる：
**「設計判断を全部引き受けてしまうライブラリ」は、利点として数えない。**
ライブラリが全部やってくれる領域は、成果物が何も残らないからだ。
→ **CRDT を使わない・エディタは自作しない**（第7章）、**Django を却下**（第4章）の共通の軸。

### 制約4：Python 側のエコシステムに中核が寄っている

- **MCP サーバー**：仕様策定元が Anthropic で、公式 SDK は Python が一級
- **Claude API による記事変換**（Qiita ⇄ note ⇄ X 280字）：公式 SDK `anthropic` は Python が最も成熟
- **50万行の分析**：重い集計を SQL から Python 側へ逃がす余地が要る

この3つのうち2つは**このアプリの差別化要素そのもの**。→ **FastAPI へ切り替えた**決定打（第4章）。

## 2. 全体像

```
ブラウザ ──┐
Claude Code ├──→  FastAPI (Python)  ──→  PostgreSQL
ジョブ ─────┘         │
                      └─ MCP サーバー / チャネルアダプタ / ジョブワーカー
                         （すべて Service 層を経由する）

ブラウザ ──→  Next.js 16  ──(BFF: 認証の中継だけ)──→  FastAPI
```

- **フロントとバックエンドは別アプリ**（ADR-0010）
- ブラウザは FastAPI を直接叩かない。**Next.js が認証を中継する**（BFF、ADR-0014）
- MCP・ジョブ・チャネル連携は**画面と同じ Service を通る**。抜け道を作らない（ADR-0009）

---

## 3. なぜフロントとバックエンドを「分離」するのか（ADR-0010）

Next.js を使うなら、API を Next.js 側（Route Handlers）に同居させて1アプリにする手もある。
それをやらない理由は制約1に尽きる。

- **MCP サーバーとジョブは、ブラウザと無関係に API を叩く。**
  API を Next.js に同居させると、これらが Next.js のランタイムに巻き込まれる。
  「Claude Code からの呼び出し」のために Next.js を起動する、という不自然な構造になる。
- 制約3のため、**API が単体で読める・単体でテストできる・単体でデプロイできる**ことに意味がある。

代償：デプロイ対象が2つになる。CORS の心配が出る
（→ これは ADR-0014 の BFF で消える。ブラウザは FastAPI を直接叩かないため）。

## 4. バックエンド：なぜ FastAPI なのか（ADR-0001 → ADR-0012）

ここが選定の山場。**一度 NestJS に決めて、後から FastAPI に覆した。**
「覆した」こと自体が、制約の変化を記録した良い例なので、順を追う。

### 4-1. まず NestJS を選んだ（ADR-0001）

当初はバックエンドも TypeScript の予定だった。候補は NestJS / Express / Fastify / Hono / tRPC。
**NestJS を選んだ理由は3つ：**

1. **既存の設計経験がそのまま移植できる。**
   筆者は Laravel（PHP）の実務経験がある。NestJS は Laravel とほぼ同型：

   | Laravel | NestJS |
   |---|---|
   | サービスコンテナ | DI コンテナ |
   | サービスプロバイダ | Module |
   | ミドルウェア | Guard / Interceptor |
   | FormRequest | DTO + ValidationPipe |
   | Eloquent | Prisma / TypeORM |

   → **未経験なのは「言語」であって「設計」ではない**（制約2に効く）。

2. **フレームワークが構造を強制する。**
   1人で4ヶ月書き続けると、自由すぎるフレームワーク（Express）では構造が崩れる。
   NestJS は Module / Controller / Service の型が決まっていて、後から読んでも追える。

3. **DI があるのでテストが書ける。** Service のテストで Repository をモックに差し替えられる。

（tRPC は「型安全性は最強だが、外部から叩かれる入り口＝MCP がある以上 REST + OpenAPI のほうが素直」で却下。）

### 4-2. なぜ覆したのか（ADR-0012）

ADR-0001 の後、ADR-0004〜0011 で設計を詰めた結果、
**ADR-0001 の選択肢の表に無かった要件が3つ確定した**（＝制約4）：

1. MCP サーバーをサービス側に実装する（ADR-0007）
2. Claude API による下書き変換をジョブで走らせる（ADR-0011）
3. 50万行の指標スナップショットを分析する（非機能要件）

いずれも**フレームワークの選定軸そのものを変える**。しかも
**まだコードを1行も書いていない**ので、切り替えコストが実質ゼロの唯一のタイミングだった。

### 4-3. FastAPI を選んだ理由

1. **アプリの中核が Python のエコシステムに寄っている**（制約4）。
   薄いほう（Node の `mcp` / `anthropic`）に賭ける理由がない。

2. **ADR-0001 が残した「OpenAPI の宿題」が構造的に解ける。**
   tRPC を捨てた分、フロントとの型共有を OpenAPI 生成で埋める必要があった。
   FastAPI は Pydantic のスキーマから **OpenAPI を自動生成する**。
   「API 仕様を OpenAPI で公開」が**作業ではなく初期状態**になる。
   フロントの型はこの OpenAPI から生成する（手書きしない）。

3. **外部データの境界でバリデーションが型と一体になる。**
   チャネルアダプタは Qiita API・RSS・note から**信用できない外部データ**を受け取る。
   Pydantic は「バリデーション」と「型定義」が同じ宣言なので、
   「境界で検証し、内側は検証済みの型しか流れない」を構造として担保できる。

4. **設計を自分で組む余地が残る**（制約3）。← これが Django を却下した理由でもある。

### 4-4. なぜ Django ではないのか

Django なら認証・ORM・管理画面が最初から揃い、完成は最も早い。
だが**設計する対象が消える**。制約3（設計が成果物）と正面から噛み合わない。
これは後述の「CRDT を使わない」と**まったく同じ判断軸**。

### 4-5. 覆した代償：構造の強制が失われた

NestJS の利点2「フレームワークが構造を強制する」は **FastAPI では成立しない。**
`Controller → Service → Repository` を**規約として自分で守る**必要がある。
「気をつける」で守ると必ず崩れるので、**仕組みで守る**（第6章）。

## 5. ORM：なぜ SQLAlchemy 2.0 なのか（ADR-0002）

FastAPI に決まった時点で、ORM 候補は **SQLAlchemy 2.0 / SQLModel / Tortoise ORM** に変わった。
選定軸を決めたのは主に2つ。

### 5-1. 複雑な SQL に「逃げ道」が要る

分析クエリ（公開後 N 日の伸びカーブ＝ウィンドウ関数、公開月コホート、タグ別集計）を
50万行に対して2秒以内で返す必要がある。

- **SQLAlchemy** は ORM と **Core**（SQL をほぼそのまま式で組み立てる低レベル API）を
  **同じ接続・同じトランザクションで併用できる**。
  普通の CRUD は ORM、重い分析は Core、逃げ切れなければ生 SQL文字列(`text()`)、の三段構えが1ライブラリで完結。
- **Tortoise** はこの層が弱く、ウィンドウ関数は生 SQL に落ちやすい。そのとき型も接続管理もライブラリの外に出る。
- **SQLModel** は複雑クエリで結局 SQLAlchemy Core に降りる。なら最初から SQLAlchemy でよい。

### 5-2. 永続化を Repository に閉じ込められる（第6章と噛み合う）

SQLAlchemy は **Data Mapper + Unit of Work** 型。
「モデルが自分を保存する」**ActiveRecord ではない**（Laravel の Eloquent、Django ORM はこちら）。

```
Eloquent:        $content->save();          ← モデルが永続化の責務を持つ
SQLAlchemy:      session.add(content);      ← セッション（Repository）が永続化を担う
                 await session.commit();
```

`AsyncSession` を Repository の中だけで扱い、Service にはドメインオブジェクトで返す、
という**層の分離が自然に組める**。
Tortoise の `await content.save()` はこの境界を溶かす方向に働く。

さらに `.importlinter` に **「Service から `sqlalchemy` を import してはいけない」** という契約を書けて、
層の分離を CI で担保できる（第6章）。

### 5-3. SQLModel を落とした理由 — またしても「設計を引き受けるから」

SQLModel の中心的な売りは、**ORM モデルと Pydantic スキーマを1クラスに統合する**こと。
Reverb は `models.py`（テーブルの形）と `schemas.py`（API リクエスト/レスポンスの形）を
**意図的に分けている**（ライフサイクルも変更理由も違うため）。
SQLModel はこの構造と正面から反する。→ ADR-0004・ADR-0012 と同じ軸で、利点として数えない。

### 5-4. その他の決め手（軽く）

- **マイグレーションは Alembic 一択**。SQLAlchemy と同じ作者で、メタデータをそのまま autogenerate に使える。
  Tortoise だと Aerich になり、確定済みの標準と食い違う。
- **楽観ロック**（古い version での更新を 409 で弾く）が `version_id_col` の設定だけで入る。自前で WHERE 条件を書かない。
- **型**：2.0 は `Mapped[]` アノテーションで mypy と整合する。1.x を避けて 2.0 系に限定するのはこのため。

## 6. レイヤードアーキテクチャと「仕組みで守る」（ADR-0009）

制約1（入り口3つ）への答え。

```
router.py  ──→  service.py  ──→  repository.py  ──→  DB
（HTTP のみ）   （業務ルール・認可）  （SQLAlchemy）
```

- **業務ルールと認可は Service に集約する。** 3つの入り口すべてが同じ Service を通る。
  「公開は owner のみ」を router に書くと、MCP 経由の `publish` でチェックが漏れる。
- **Service は HTTP を知らない。** FastAPI の `Request` / `Response` を Service に持ち込むと、
  ジョブや MCP から呼べなくなる（最も起きやすい崩れ方）。
- **Repository は業務判断を持たない。** 「公開済みは除外」を Repository に書くと、別のユースケースで再利用できない。

### FastAPI は層を強制しない → CI で強制する

NestJS と違い、この一方向依存はフレームワークが守ってくれない。だから**壊れたら CI が赤くなる**状態にする：

| 仕組み | 役割 |
|---|---|
| ディレクトリで層を物理的に分ける | `router.py` / `service.py` / `repository.py` を層ごと固定名に |
| DI を FastAPI の `Depends` に寄せる | Service を router で直接 import して組み立てない |
| **`import-linter`（`lint-imports`）** | 層をまたぐ import・`service.py` からの `sqlalchemy` / `fastapi` import・`core` からの `modules` import を CI で検出して落とす |

`import-linter` は「規約ではなく仕組みで守る」の本命。
フロント側の「OpenAPI 生成を CI に組み込んでスキーマとズレたら落とす」も**まったく同じ発想**。

## 7. フロントエンド：Next.js 16 と BFF 認証（ADR-0014）

### トークンをどこに置くか

このアプリは**他人が書いた Markdown**（記事本文・レビューコメント・外部から取り込んだ記事）を
常時描画する。**XSS の攻撃面が構造的に広い。**
アクセストークンを JavaScript から読める場所（`localStorage` 等）に置くと、XSS 一発で盗まれる。

→ トークンは **httpOnly Cookie**（JS から読めない）に置き、
**Next.js を認証の中継役（BFF）として通す**。
BFF がやるのは「Cookie ⇄ `Authorization` ヘッダの載せ替え」と「未ログイン時のリダイレクト」だけ。
**業務ロジックと認可判断は持たせない**（それは FastAPI の Service の仕事）。

### フロントの設計も成果物に含む

「Markdown エディタは既製品を使う（自作しない）」が、**フロント全体が対象外という意味ではない**。
状態管理（サーバー状態 / プッシュ由来のサーバー状態 / クライアント状態の3分類）、
Server / Client Component の境界、BFF 経由の認証は**設計対象**として ADR / steering に残す。

> Next.js 16 はトレーニングデータ上の慣習と破壊的に違う。コードを書く前に
> `frontend/node_modules/next/dist/docs/` で現行仕様を必ず確認する（記憶で書かない）。

## 8. 「設計を引き受けるライブラリは使わない」— 全体を貫く1本の軸

同じ判断が、選定のあちこちで繰り返されている。

| 場面 | 却下したもの | 理由（すべて同じ） |
|---|---|---|
| フレームワーク | Django | 認証・ORM・管理画面を最初から与え、**設計する対象が消える** |
| フレームワーク | NestJS の「構造の強制」 | この目的では利点に数えない（自分で層を設計して ADR に残すほうが適う） |
| ORM | SQLModel | モデルとスキーマの統合という**設計判断を引き受けてしまう** |
| 共同編集 | Yjs（CRDT） | 排他制御を全部引き受け、**バックエンドの設計が成果物として残らない** |

一方で、**設計の対象でない領域は迷わず既製品を使う**：

| 場面 | 採用 | 理由 |
|---|---|---|
| Markdown エディタ | CodeMirror 6 / tiptap（未定・自作しない） | エディタそのものは本プロジェクトの設計対象ではない |
| OpenAPI 生成 | FastAPI 標準 | 型共有は仕組みで担保したいだけ。手で書く価値がない |
| マイグレーション | Alembic | SQLAlchemy と一体。ここで独自性を出す意味がない |

**「これは自分で設計して説明できるようにすべき部分か？ それとも解けた問題か？」**
——この問いが、Reverb の技術選定のほぼすべてを決めている。

## 9. 用語集

| 用語 | 意味 |
|---|---|
| **ADR** | Architecture Decision Record。1つの設計判断と、却下案を却下した理由を残す文書 |
| **BFF** | Backend For Frontend。フロント専用の薄い中継層。ここでは Next.js が担い、認証の載せ替えだけを行う |
| **MCP** | Model Context Protocol。AI エージェント（Claude Code）がツールを呼ぶための仕様。Anthropic 策定 |
| **Data Mapper / ActiveRecord** | 永続化の責務をどこに置くか。Mapper はセッション側（SQLAlchemy）、ActiveRecord はモデル自身（Eloquent / Django ORM） |
| **Unit of Work** | 一連の変更をまとめて1トランザクションで確定する仕組み。SQLAlchemy の `AsyncSession` がこれ |
| **SQLAlchemy Core** | ORM の下にある低レベル API。SQL の構造を Python の式で組み立てる。分析クエリの逃げ道 |
| **楽観ロック** | 行をロックせず、バージョン番号で「更新の間に他人が書いたか」を検出する方式 |
| **CRDT** | 競合が自動でマージされるデータ構造。Yjs が代表。Reverb は使わず、ロックを自前設計する |
| **import-linter** | モジュール間の import 依存に契約を書き、違反を CI で落とす Python ツール。コマンドは `lint-imports` |

## 10. まとめ — 選定の要約

- **分離**（ADR-0010）：入り口が3つあるので、API は単体で立つ必要がある
- **FastAPI**（ADR-0012）：中核（MCP / Claude / 分析）が Python 側にある。OpenAPI が標準。設計の余地が残る
  - 代償の「構造の強制の喪失」は **import-linter** で埋める（ADR-0009）
- **SQLAlchemy 2.0**（ADR-0002）：Core が複雑 SQL の逃げ道になる。Data Mapper で層の分離が自然。Alembic と一体
- **Next.js 16 + BFF**（ADR-0014）：他人の Markdown を描く＝XSS 面が広い。トークンは httpOnly Cookie、Next は中継だけ
- 全体を貫く軸：**設計して説明すべき部分は自分で組む。解けた問題は既製品に任せる**
