# foundation 設計レビュー 解説

**「なぜその修正が正しいのか」を、背景の仕組みから説明するドキュメント。**

---

## 0. このドキュメントについて

### 何のための文書か

Reverb というアプリの最初の設計書（`design.md`）に対してレビューを行い、16箇所を修正した。
この文書は、**その修正の一つひとつが「なぜ必要だったのか」を、前提知識から順に説明する**ためのもの。

設計書そのものは「こう作る」という結論だけを書く。結論だけでは、後から読んだときに
「なぜこうなっているのか」が分からなくなる。この文書はその隙間を埋める。

### 想定する読者

- バックエンド開発の経験はあるが、**Python / FastAPI / SQLAlchemy は初めて**という人
- Laravel（PHP）または Spring Boot（Java）の経験がある人には、対応する概念を随時示す

### 前提：Reverb とはどんなアプリか

**「書いたあとに何が起きたか」を記録し続けるための箱。**

技術記事（Qiita）、エッセイ（note）、SNS（X）、ポッドキャストという複数の発信チャネルを持つ人が、
「ネタを思いついてから、記事を書いて、公開して、その後どれだけ読まれたか」までを1本の線でつなぐアプリ。

特徴的なのは最後の部分で、**各プラットフォームは「今の数字」しか見せてくれない**。
「公開3日後に伸びたのか、じわじわ伸びたのか」を知るには、毎日その数字を記録し続けるしかない。
これが Web アプリケーションとして作る必然性になっている。

技術構成は、バックエンドが Python の FastAPI、データベースが PostgreSQL、
ORM（データベースとプログラムをつなぐ層）が SQLAlchemy 2.0、フロントエンドが Next.js。

### 今回のレビュー対象「foundation」とは

Reverb を作るうえで**最初に据える土台**の設計。次の3つを扱う。

1. **認証（Authentication）** — 「あなたは誰か」を確かめる。ログインの仕組み
2. **認可（Authorization）** — 「あなたは何をしてよいか」を決める。権限の仕組み
3. **コンテンツの器** — ネタを登録し、「受信箱 → 採用 → 執筆中 → レビュー中 → 公開済」と状態を進める仕組み

この3つが動けば、後続の機能はすべてこの上に乗せるだけになる。だから最初に作る。

## 1. 予備知識 — 修正内容を読む前に

修正の話に入る前に、繰り返し出てくる5つの概念を先に押さえる。
すでに知っているものは飛ばしてよい。

### 1-1. レイヤードアーキテクチャ（Controller / Service / Repository）

プログラムを**役割ごとの層に分け、依存の向きを一方向に固定する**設計。

| 層 | 役割 | やってはいけないこと |
|---|---|---|
| **Controller**（FastAPI では Router） | HTTP を受け取る。URL・リクエストの形・ステータスコードを扱う | 業務の判断をする |
| **Service** | 業務ルールを持つ。「誰が何をしてよいか」「この状態から次の状態へ進めるか」 | HTTP を知る |
| **Repository** | データベースへの読み書き。SQL の組み立て | 業務の判断をする |

依存は `Controller → Service → Repository` の一方向だけ。**下の層が上の層を呼び出すのは禁止。**

Laravel なら Controller / Service クラス / Repository クラス、
Spring なら `@RestController` / `@Service` / `@Repository` にそのまま対応する。

**Reverb でこれが特に重要な理由**は、このアプリに**入口が3つある**ことにある。

1. ブラウザからの HTTP リクエスト
2. Claude Code（AI エージェント）からの MCP という仕組み経由の呼び出し
3. 毎日自動で走るバッチ処理

3つが同じデータを同じルールで操作する。もし「公開できるのはオーナーだけ」というルールを
Controller に書いてしまうと、**MCP から公開されたときにそのチェックが通らない**。
権限チェックが二重実装になり、いつか必ずズレる。ズレた瞬間にセキュリティホールになる。

だから**業務ルールと権限判定は Service に集約する**。これが設計全体を貫く芯になっている。

### 1-2. 認証（401）と認可（403）の違い

よく混同されるが、まったく別のもの。

- **認証（Authentication）** = 「あなたは誰ですか」。失敗すると **HTTP 401 Unauthorized**
- **認可（Authorization）** = 「あなたはそれをしてよいですか」。失敗すると **HTTP 403 Forbidden**

401 は「名乗り直してください」、403 は「あなただと分かったうえで、それは駄目です」。

クライアント側の挙動が変わるので、この区別は実務的に効く。
**401 を受け取ったらログイン画面に飛ばす**が、403 で飛ばしてはいけない（ログインし直しても解決しないため)。

### 1-3. トランザクションと commit、そして flush

データベースは「まとめて実行し、まとめて確定する」仕組みを持っている。これがトランザクション。

ここで **Laravel（Eloquent）と SQLAlchemy の決定的な違い**が出る。ここは今回の修正の核心なので丁寧に見る。

**Laravel の Eloquent は Active Record パターン。**

```php
$post->title = "新しいタイトル";
$post->save();   // この瞬間に UPDATE 文がデータベースへ飛ぶ
```

モデル自身が「自分を保存する」責務を持っていて、`save()` を呼んだ瞬間に SQL が発行される。

**SQLAlchemy は Data Mapper + Unit of Work パターン。**（Spring の JPA / `EntityManager` と同じ系統）

```python
content.title = "新しいタイトル"
# ← この時点では、まだ何も SQL は飛んでいない
```

SQLAlchemy は `Session`（セッション）という作業スペースを持ち、
**「このオブジェクトを変更した」という記憶を溜めておく**。SQL の発行は先送りされる。

溜まった変更を実際に SQL として送り出す操作が2つある。

| 操作 | 何が起きるか |
|---|---|
| **`flush()`** | 溜まった変更を **SQL としてデータベースへ送る**。ただし、まだ確定はしない（トランザクションの中） |
| **`commit()`** | トランザクションを**確定**する。以後、他の人からも見えるようになり、取り消せなくなる |

**ここが重要**：`flush()` を呼ばずに `commit()` すると、SQLAlchemy は commit の直前に自動で flush する。
つまり **SQL の送信と確定が同じ瞬間に起きる**。

なぜこれが問題になるかは、後の「修正7」で詳しく扱う。
今は「**SQLAlchemy では、コードを書いた場所と SQL が飛ぶ場所がズレる**」とだけ覚えておけばよい。

Spring Boot で `@Transactional` を付けたメソッドの中で、実際にいつ SQL が飛んでいるかを
意識したことがあるなら、それと同じ話をしている。違いは、**Spring はそれをフレームワークが隠すが、
FastAPI は自分で配線する**という点にある。

### 1-4. 楽観ロック

複数の人が同じデータを同時に編集したときの衝突を防ぐ仕組み。

**悲観ロック**は「編集中は他の人が触れないよう鍵をかける」。確実だが、鍵が残ったままになると誰も編集できなくなる。

**楽観ロック**は「鍵をかけず、保存するときに衝突を検出する」。

やり方はシンプルで、データに `version` という番号を持たせる。

1. A さんがデータを読む（version = 7）
2. B さんも同じデータを読む（version = 7）
3. A さんが保存 → `UPDATE ... WHERE id = 42 AND version = 7` が成功し、version は 8 になる
4. B さんが保存 → `UPDATE ... WHERE id = 42 AND version = 7` が **0 行しか更新しない**（もう version は 8 なので）
5. 0 行 = 衝突が起きたと判定し、B さんに **HTTP 409 Conflict** を返す

Reverb では、共同編集の衝突をこの方法で自前で解決する方針を採っている。

### 1-5. 「規約」ではなく「仕組み」で守る

設計ルールを守る方法は2つある。

- **規約**：ドキュメントに書き、レビューで人間が見る。→ **いつか必ず破られる**
- **仕組み**：破ったらツールが自動で検出し、CI（自動テストの実行環境）が赤くなる

Reverb は「層をまたぐ依存の禁止」を**仕組み**で守る方針を採っている。
使うツールが **import-linter**。Java の **ArchUnit** に相当するもので、
「このモジュールはこのモジュールを import してはいけない」というルールを設定ファイルに書き、
違反があればテストと同じ扱いで失敗させる。

なぜこれが要るのか。**Spring や NestJS と違い、FastAPI は層構造を強制しない。**
FastAPI は「こういうディレクトリ構造にしなさい」と言わないフレームワークなので、
Repository を Controller から直接呼ぶコードを書いても、何も起きずに動いてしまう。
だから外部ツールで縛る。

### 修正1：最初のユーザーを作る方法が、どこにも無かった

#### 何が書いてあったか

Reverb は**招待制**のアプリとして設計されている。誰でも勝手に登録できる「サインアップ画面」を持たない。
これは意図的な判断で、**自己登録を無くせば、不特定多数の個人情報を扱わずに済む**という狙いがある。

設計書には、こう書かれていた。

- 自己登録のための API は存在しない
- ユーザーが増える唯一の経路は「招待を受諾する」こと
- 招待を発行できるのは、企画（プロジェクト）のオーナーだけ
- 企画を作れるのは、ログイン済みのユーザー

#### 何が問題か

**この4つを並べると、循環している。**

> ログインするにはユーザーが必要
> → ユーザーになるには招待が必要
> → 招待を出すにはオーナーが必要
> → オーナーになるには企画を作る必要がある
> → 企画を作るにはログインが必要 → **最初に戻る**

**誰も、一度も、システムに入れない。**

これは「セキュリティが厳しすぎる」という話ではなく、単純に**アプリが起動しない**ということ。
このマイルストーンの完了条件は「ログインして、企画を作り、ネタを登録して状態を動かせる」なのに、
1歩目のログインに到達できない。

#### なぜ設計時に気づかなかったのか

**「機能」を考えていて、「初期状態」を考えていなかったから。**

これは招待制・承認制のシステムで**必ず起きる**問題で、「鶏が先か卵が先か」の構造をしている。
機能の要件だけを丁寧に詰めても、この穴は見えない。
穴が見えるのは、「では、まっさらなデータベースから始めて、最初の1手は何か」と問うたときだけ。

#### どう直したか

**HTTP を経由しない管理コマンドを1本用意する**ことにした。

```bash
docker compose exec backend python -m app.cli create-user \
    --email owner@example.com --display-name まんどぅ
```

Laravel でいう `php artisan` コマンド、Spring でいう `CommandLineRunner` や
起動時のデータ投入スクリプトに相当する。

**なぜ API ではなく CLI（コマンドライン）なのか。** ここが判断のポイント。

「最初のユーザーを作る API」を作ると、それは**招待制を迂回する入口を恒久的に開ける**ことになる。
どれだけ厳重に守っても、存在する限り攻撃対象になる。
一方 CLI は、**サーバーに入れる人だけが実行できる**。すでにサーバーに入れる人は何でもできるので、
新しい攻撃面が増えない。

**なぜデータベースのマイグレーションに書かないのか。**
マイグレーション（データベースの構造変更を記録するファイル）は、
開発環境・本番環境すべてで同じものが実行される共有の履歴。
そこにメールアドレスやパスワードを書くと、**環境ごとに違うべき値が履歴に固定されてしまう**。

同じ仕組みで、**デモアカウント**（採用面談などで「触ってみてください」と URL を渡すための読み取り専用アカウント）も
払い出せるようにした。これも設計書に「作り方」が書かれていなかったもの。

#### 教訓

> **入口を閉じる設計をしたら、必ず「自分が入るための鍵」を別に用意する。
> そしてその鍵は、閉じた入口とは別の経路（HTTP の外）に置く。**

### 修正2：デモアカウントが、企画を作れてしまう

#### 前提：Reverb の権限モデル

Reverb は**企画（プロジェクト）を共有の単位**とし、企画ごとに3つの役割を割り当てる。

| 役割 | できること |
|---|---|
| **owner**（オーナー） | 全部。メンバーの招待・除名、公開 |
| **editor**（共同編集者） | 執筆・編集はできるが、公開はできない |
| **reviewer**（レビュアー） | 閲覧とコメントだけ |

これに加えて、役割とは**別の軸**で **demo**（デモアカウント）という制約がある。
デモは「どんな役割を持っていても、読むことしかできない」。

#### 何が書いてあったか

権限チェックを行う `ProjectAuthorizer` というクラスが、こう設計されていた。

```python
async def require(self, actor, project_id, perm):
    # 1. この人はこの企画で何の役割か？
    role = await self._members.role_of(actor.user_id, project_id)
    if role is None:
        raise NotFoundError("project")     # メンバーではない → 404

    # 2. その役割に、この権限はあるか？
    allowed = ROLE_PERMISSIONS[role]

    # 3. デモアカウントなら、閲覧系だけに絞り込む
    if actor.is_demo:
        allowed = allowed & VIEW_ONLY

    if perm not in allowed:
        raise ForbiddenError(perm)         # → 403
```

丁寧に書けているように見える。デモの制限もちゃんと入っている。

#### 何が問題か

**この関数は `project_id`（企画の ID）を引数に取る。**

ということは、**企画がまだ存在しない操作には、この関数を呼べない。**

該当するのが「**企画を新規作成する**」操作。まだ企画が無いのだから、`project_id` は渡せない。
結果として、企画作成の処理は**この権限チェックをまるごと通らない**。

要件では、デモアカウントの企画作成は明確に「不可」となっている。
だが設計上、**デモアカウントで無限に企画を作れてしまう**。

同じ穴が「招待を受諾する」操作にもある。デモアカウントが招待リンクを踏むと、
企画のメンバーとして参加できてしまう。

#### なぜこれが起きるのか — 認可には2種類ある

これは Reverb 固有の話ではなく、**権限設計で一般的に起きる型**。

| 種類 | 判定に必要なもの | 例 |
|---|---|---|
| **リソースに紐づく認可** | 主体 ＋ 対象リソース | 「この企画のこのコンテンツを編集してよいか」 |
| **主体そのものの属性による制限** | 主体だけ | 「そもそもこのアカウントは書き込みをしてよいか」 |

`ProjectAuthorizer` は前者しか実装していなかった。だから**後者だけで判定すべき操作が素通りする**。

**Laravel を使ったことがあるなら、これはまさに Policy の `create` メソッドの話。**
Laravel の Policy は通常 `update(User $user, Post $post)` のようにモデルを受け取るが、
`create(User $user)` だけはモデルを取らない。**まだ存在しないから**。
Laravel はこの非対称性をフレームワークとして扱っているが、自前で認可を書くとここが抜ける。

#### どう直したか

企画に紐づかないガードを別に用意した。

```python
def require_not_demo(actor) -> None:
    if actor.is_demo:
        raise ForbiddenError("demo account is read-only")
```

そして設計書に、**2つのガードで漏れなく覆う**ことを明記した。

- 企画配下の操作 → `ProjectAuthorizer.require`（役割 × デモ制限）
- 企画に紐づかない操作 → `require_not_demo`

#### 教訓

> **認可の穴は「権限表に載っていない操作」ではなく、
> 「権限表の判定関数が、そもそも呼べない操作」に開く。**

権限マトリクスの表を作ったら、その表の全行について
「**この判定を、どの関数のどこで実行するのか**」を1行ずつ指させるか確認する。
指せない行があったら、そこが穴。

### 修正3：トークンが無いときに、401 ではなく 422 が返る

#### 何が書いてあったか

ログイン後のリクエストは `Authorization: Bearer <トークン>` というヘッダーを付けて送る。
そのヘッダーを読み取ってユーザーを特定する処理が、こう書かれていた。

```python
async def get_current_actor(
    authorization: str = Header(...),      # ← ここ
    ...
):
```

Python の `...`（3つのドット。`Ellipsis` という値）は、FastAPI では「**このパラメータは必須**」を意味する。

#### 何が問題か

**ヘッダーが無いとき、FastAPI は 401 ではなく 422 を返す。**

要件には明確に「トークンが無い／不正／期限切れのリクエストは **401** で拒否される」と書いてある。仕様違反。

#### なぜそうなるのか

FastAPI には**バリデーション（入力検証）の仕組み**が組み込まれている。
リクエストの形（必須パラメータが揃っているか、型が合っているか）を、
**あなたが書いた関数の中身が実行される前**に検査する。

ここで「必須」と宣言したパラメータが無いと、FastAPI は
「これは入力の形式エラーだ」と判断し、`RequestValidationError` を投げる。
そして FastAPI の既定では、これは **HTTP 422 Unprocessable Entity** になる。

つまり、**あなたが書いた `AuthenticationError`（401）を投げるコードには、そもそも到達していない**。

FastAPI から見れば正しい動作で、**「ヘッダーが足りない」は入力の不備**。
だが仕様から見れば、これは**認証の失敗**であって、意味論が違う。

#### なぜ実害があるのか

このアプリは、フロントエンド（Next.js）がクッキーからトークンを取り出して
バックエンドに中継する構成になっている。フロントエンドは
**「401 が返ってきたらログイン画面へリダイレクトする」**という作りにする。

トークンの期限が切れてクッキーが消えた状態でページを開くと、
本来は 401 が返ってログイン画面に飛ぶべきところ、**422 が返るのでリダイレクトが働かない**。
ユーザーから見ると「画面が壊れて、ログインし直す方法も分からない」状態になる。

#### どう直したか

```python
async def get_current_actor(
    authorization: str | None = Header(default=None),   # 任意で受ける
    ...
):
    if authorization is None:
        raise AuthenticationError()                     # 自分で 401 を投げる
```

**「必須」をフレームワークに任せず、自分で受け取って自分で判断する。**

ついでに、この関数がセッションとユーザーを2回に分けてデータベースに問い合わせていたのを、
1回の JOIN にまとめた。**この処理は認証が要る全リクエストで必ず走る**ので、
問い合わせが1回減ることの効果が全体に効く。

#### 教訓

> **フレームワークの「便利なデフォルト」が、仕様の意味論とズレることがある。
> HTTP ステータスコードは仕様が決めるものであって、フレームワークが決めるものではない。**

特に「認証」は、フレームワークのバリデーション機構と**責務が重なる**ので事故が起きやすい。

### 修正4：層のチェックツールの設定が、そのままでは動かない

#### 何が書いてあったか

予備知識 1-5 で触れた import-linter の設定が、こう書かれていた。

```ini
[importlinter:contract:layers]
type = layers
layers =
    app.modules.(auth|projects|contents).router
    app.modules.(auth|projects|contents).service
    app.modules.(auth|projects|contents).repository
containers = app
```

意図は明確で、「router は service を呼んでよい、service は repository を呼んでよい、しかし逆は駄目」。

#### 何が問題か

**`containers` と `layers` の関係を取り違えている。**

import-linter の `layers` 契約では、
**`layers` に書く名前は `containers` からの相対名**として解釈される。

`containers = app` と書いたうえで `layers` に `app.modules.auth.router` と書くと、
ツールは `app` + `app.modules.auth.router` = **`app.app.modules.auth.router`** という
存在しないモジュールを探しに行く。

#### 何が本当に怖いのか

設定が壊れていることそのものより、**壊れた検査が「緑」を出し続けること**のほうが怖い。

「層の依存は CI で守られている」と信じたまま、実際には何も検査されていない状態が続く。
半年後、層がぐちゃぐちゃになってから気づく。

**チェックが無い状態より、壊れたチェックがある状態のほうが危険。**
無ければ人は注意するが、あると安心してしまう。

#### どう直したか

`containers` に3つのモジュールを並べ、`layers` は相対名の3行だけにした。

```ini
[importlinter:contract:layers]
type = layers
containers =
    app.modules.auth
    app.modules.projects
    app.modules.contents
layers =
    router
    service
    repository
```

こう書くと、意図がそのまま形に出る。
**「auth・projects・contents という3つの箱があり、それぞれの中に router・service・repository が
この順で積まれている」**と読める。

#### 教訓

> **CI で守る仕組みを入れたら、必ず一度「わざと壊して、赤くなること」を確認する。**

ルールを書いた後、意図的に違反するコード（Service から Repository を飛び越えて import する、など）を
1行書いてツールを走らせる。赤くならなければ、設定が効いていない。
これを**セットアップの一部として必ずやる**。

### 修正5：チェックツールが、設計判断と正面衝突する

#### 何が書いてあったか

もう1つのルールとして、こう書かれていた。

```ini
[importlinter:contract:service-no-sqlalchemy]
type = forbidden
source_modules = app.modules.contents.service     # Service 層は
forbidden_modules = sqlalchemy                    # SQLAlchemy を知ってはいけない
```

**「Service 層がデータベースの道具を直接触ってはいけない」**というルール。
Service に SQL を書き始めると、Repository 層を作った意味が消えるので、これは正しい意図。

一方、同じ設計書の別の場所には、こう書かれていた。

> 現時点では、Repository はデータベースのモデルオブジェクトを、そのまま Service に返す。

これは実装量を抑えるための現実的な判断で、それ自体は妥当。

#### 何が問題か

**この2つは両立しない。**

Service がデータベースのモデルを受け取るなら、Service のコードには型の注釈が要る。

```python
# service.py
from app.modules.contents.models import Content   # モデルを import する

async def update(...) -> Content:                 # 戻り値の型として使う
```

そして `models.py` は当然 SQLAlchemy を import している。つまり、

> `service.py` → `models.py` → `sqlalchemy`

という**連鎖**ができる。

**import-linter の `forbidden` 契約は、既定でこの連鎖（間接 import）も違反として報告する。**
直接 import していなくても、「たどり着けるなら違反」と判定する。

結果、**最初のモジュールを書いた瞬間に CI が赤くなり、そのままでは1行も進めない。**

#### どう判断したか

ここで選択肢は2つある。

| 選択肢 | 内容 | 代償 |
|---|---|---|
| **(a) チェックを緩める** | 「直接 import しないこと」だけを検査する設定にする | ルールがやや緩くなる |
| **(b) 設計を変える** | Repository がモデルを返すのをやめ、専用のデータ型に詰め替える | 実装量が増える |

**(a) を選んだ。** 判断の根拠はこう。

> **このルールが本当に防ぎたかったのは何か？**
>
> 防ぎたいのは「**Service がデータベース接続を握って、直接クエリを書き始めること**」。
> 「Service がモデルの型を知っていること」ではない。

ルールの**文言**ではなく**意図**に照らすと、(a) は意図を損なわない。

設定に `allow_indirect_imports = True` を1行足し、
**なぜこの行があるのかを設計書に明記した**。これがないと、後で読んだ人（半年後の自分）が
「なぜ緩めてあるのか」が分からず、消してしまう。

さらに「**もし後で設計を (b) に変えるなら、この行も外す**」と、
2つの判断がセットで動くことを書き添えた。

#### 教訓

> **自動チェックが「誤検知」したとき、選択肢は「チェックを緩める」か「設計を変える」の二択。
> 判断の基準は、そのルールが何を防ぎたかったのかに戻ること。**

そして緩めたなら、**緩めた理由を必ず書き残す**。理由のない例外は、次の例外を呼ぶ。

### 修正6：土台が、その上に乗るものを知ってしまっている

#### 何が書いてあったか

Reverb のコードは、大きく2つに分かれている。

- **`core/`** — 土台。設定、データベース接続、パスワード処理、権限判定の枠組み
- **`modules/`** — 機能ごとのまとまり。`auth`（認証）、`projects`（企画）、`contents`（コンテンツ）

権限判定を行う `ProjectAuthorizer` は `core/` に置かれていた。そして、こう書かれていた。

```python
# core/authorization.py
from app.modules.projects.repository import ProjectMemberRepository   # ← 問題はここ

class ProjectAuthorizer:
    def __init__(self, members: ProjectMemberRepository):
        ...
```

「この人はこの企画で何の役割か」を調べるために、企画モジュールの Repository が必要だった。

#### 何が問題か

**土台（`core`）が、その上に乗るもの（`modules`）を知ってしまっている。**

これは依存の**逆流**。土台は上物を知らないから土台でいられる。
家の基礎が2階の間取りを知っている状態を想像すると、おかしさが分かる。

実際に何が起きるかというと、こういう参照の輪ができる。

> `modules.projects.service` は `core.authorization` を使う
> `core.authorization` は `modules.projects.repository` を使う

**あと一歩で循環参照**。Python は「関数の中で import する」といった小細工で回避できてしまうが、
**その小細工が出てきた時点で設計が壊れているサイン**として扱う、というのが Reverb の方針。

#### どう直したか — 依存性逆転の原則

**`core` 側に「必要な機能の形」だけを宣言し、実物は知らないままにする。**

```python
# core/authorization.py
class MemberRoleReader(Protocol):
    """役割を1つ返せる何か。それが誰なのかは知らない。"""
    async def role_of(self, user_id: int, project_id: int) -> Role | None: ...


class ProjectAuthorizer:
    def __init__(self, members: MemberRoleReader):   # 「形」だけを要求する
        ...
```

これが **依存性逆転の原則（Dependency Inversion Principle）**。
「上位が必要とするインターフェースは、上位側に定義する」。

**Spring を書いたことがあるなら、これは見慣れた形のはず。**
ドメイン層に interface を置き、実装は infrastructure 層に置く、あの構造と同じ。

ただし **Python の `Protocol` は Java の interface と1つ違う**。

> **実装側は「これを実装します」と宣言しなくてよい。**

`ProjectMemberRepository` は `MemberRoleReader` を継承しない。
`role_of` というメソッドの形さえ一致していれば、型チェッカー（mypy）が自動的に「適合している」と判定する。
これを **構造的部分型（structural subtyping）** と呼ぶ。Go の interface と同じ考え方。

利点は、**Repository 側が `Protocol` の存在すら知らなくてよい**こと。
依存が本当に一方向だけになる。

#### さらに：この規律を仕組みで守る

これも人間の注意力に任せず、4つ目のルールとして固定した。

```ini
[importlinter:contract:core-independence]
name = core は modules を知らない
type = forbidden
source_modules = app.core
forbidden_modules = app.modules
```

うっかり `core` から `modules` を import した瞬間、CI が赤くなる。

#### 教訓

> **依存の向きが逆流していないか、「どちらが土台か」で確かめる。
> 土台が上物を知り始めたら、インターフェースを土台側に立てて向きを戻す。**

### 修正7：確定処理が、レスポンスを返した後に走っていた

**7つの中で最も分かりにくく、最も重要な修正。**
予備知識 1-3（flush と commit）が効いてくるところ。

#### 何が書いてあったか

FastAPI には **`yield` を使った依存関係（dependency with yield）** という仕組みがある。
「リクエストの前に準備し、後で片付ける」処理を書ける。

```python
async def get_session():
    async with async_session() as session:
        try:
            yield session               # ← ここでリクエスト処理に入る
            await session.commit()      # ← 処理が終わったら確定
        except Exception:
            await session.rollback()    # ← 失敗したら巻き戻す
            raise
```

**Spring の `@Transactional` を手で書いたようなもの。**
Spring では AOP のプロキシが自動でやってくれる commit / rollback を、FastAPI では自分で配線する。

意図は良い。**「1つの HTTP リクエスト = 1つのトランザクション」**を1箇所で表現できていて、
Service や Repository は commit を意識しなくてよくなる。

#### 何が問題か

**FastAPI の `yield` より後のコードは、「レスポンスを送信した後」に実行される。**

これは FastAPI 0.106 での仕様変更で、公式ドキュメントにも
「レスポンス送信後に実行されるので、ここで `HTTPException` を投げることはできない」と明記されている。

つまり、`session.commit()` が失敗したとき、
**クライアントには既に「200 OK」が返ってしまっている。**

#### なぜ commit が失敗しうるのか

ここで予備知識 1-3 が効いてくる。

**SQLAlchemy は SQL の発行を遅らせる。**
`content.title = "..."` と書いても、その瞬間には何も起きない。
`flush()` か `commit()` を呼んだときに初めて SQL が飛ぶ。

そして、**エラーは SQL が飛んだ瞬間に発生する**。

具体的に、Reverb で起きうる2つのケース。

**ケース1：楽観ロックの衝突（本来は 409 を返したい）**

修正の予備知識 1-4 で説明した `UPDATE ... WHERE id = 42 AND version = 7` が
0 行しか更新しなかったとき、SQLAlchemy は `StaleDataError` という例外を投げる。
これを捕まえて **409 Conflict** を返す設計になっている。

**ケース2：一意制約の違反（本来は適切なエラーを返したい）**

「同じ人を同じ企画に二重登録できない」という制約に違反したとき、
データベースがエラーを返す。

**どちらも、flush を明示的に呼んでいなければ commit の瞬間に初めて発火する。**
そのときにはもうレスポンスは送られた後で、**409 に変換できない**。

クライアントは「保存に成功した」と思い込み、サーバーのログにだけエラーが残る。
**最悪の壊れ方**。データが保存されていないのにユーザーは気づかない。

#### どう直したか

設計書には既に、こういう記述があった。

> Service と Repository は `flush()` までしか呼ばない。`commit()` はこの依存関係だけ。

これは元々**層の作法**として書かれていた。「commit の責任を1箇所に集めよう」という趣旨。

修正では、これを**正しさの要件に格上げ**した。

> **書き込みを伴う Service のメソッドは、戻る前に必ず `flush()` する。**

**なぜこれで解決するのか。**

`flush()` を明示的に呼べば、**SQL はその場で飛ぶ**。
つまり制約違反も楽観ロックの衝突も、**まだハンドラの中にいる間に**例外として発生する。
例外ハンドラが正しく 409 なり 422 なりに変換できる。

その後の `commit()` は「flush 済みの内容を確定するだけ」に痩せ、失敗する余地がほぼ無くなる。

**同じルールが「作法」から「正しさの要件」に変わった。**
守らなかったときの結果が「読みにくくなる」から「データが静かに壊れる」に変わったから。
設計書には、この格上げの理由を明記した。

あわせて、Service のテストで「commit する前に例外が出ること」を確認する項目を追加した。
**ルールを書くだけでなく、破られたら気づける形にする。**

#### 教訓

> **「いつ SQL が実際に飛ぶか」を把握していないと、エラーハンドリングを置く場所を間違える。**

Active Record（Laravel の Eloquent）に慣れていると、この落とし穴は見えにくい。
`save()` を呼んだ瞬間に SQL が飛ぶ世界では、**書いた場所とエラーが出る場所が一致している**から。

Unit of Work（SQLAlchemy、JPA）では**一致しない**。ここを意識するかどうかが、
このパターンを「使える」と「理解している」の境目になる。

## 3. 検討として直した9点

「動かない」ほどではないが、放置すると事故になる、あるいは判断が曖昧だったもの。
それぞれ短く扱う。

### 3-1. 招待リンクが、オーナーの降格に使えてしまう

**問題**：既にメンバーである人が別の役割の招待を受諾したとき、役割を上書きする設計だった。

すると、こういう事故が起きる。

> オーナーが1人しかいない企画で、そのオーナーが reviewer（閲覧のみ）の招待リンクを踏む
> → 役割が上書きされ、オーナーが reviewer に降格する
> → **その企画に、オーナーが1人もいなくなる**

設計書には「最後のオーナーを守る」というガードが用意されていたが、
それは「役割変更 API」と「除名 API」にしか掛かっていなかった。**招待受諾は素通り**する。

**修正**：招待を受諾しても、既存の役割は**上書きしない**（何もせず成功として扱う）。
役割の変更は「役割変更 API」の1本だけに絞った。

**教訓**：**同じ状態を変更できる経路が複数あるなら、ガードは全部に掛ける必要がある。
経路を1本に絞るほうが、たいてい安く確実。**

### 3-2. 期限切れの招待に、何を返すか

**問題**：設計書に「410 か 404」と書かれたまま、決まっていなかった。

**修正**：**404 に統一**。

**理由**：410 Gone は「以前はあったが、今は無い」という意味を持つ。
これを返すと、攻撃者に「**そのトークンは実在した**」という情報を与えてしまう。
存在しない・期限切れ・受諾済みをすべて同じ 404 にすれば、区別がつかない。

**教訓**：**エラーの応答は「正確さ」より「何を漏らさないか」で選ぶことがある。**
これは修正2で「メンバーでない人には 403 ではなく 404 を返す」としたのと同じ考え方
（403 だと「その企画は存在する」と分かってしまう）。

### 3-3. テストのデータが消えない

**問題**：テストは「トランザクションを張って、終わったら巻き戻す」ことでデータを分離したい。
だが修正7で見たとおり、アプリ側は**リクエストごとに commit する**。
素直に書くと、アプリの commit で確定してしまい、巻き戻しが効かない。

**修正**：SQLAlchemy 2.0 の `join_transaction_mode="create_savepoint"` を使う。
アプリ側の `commit()` が **SAVEPOINT（トランザクション内の途中保存点）の解放**に読み替えられ、
テスト終了時に外側を巻き戻せば全部消える。

**教訓**：**知らないと丸1日溶ける類の罠は、設計書に書いておく。**
「実装するときに調べればいい」で済むものと、済まないものがある。

### 3-4. ローカル環境でログインできない罠

**問題**：クッキーに `Secure` 属性を付けると、**HTTPS でないと保存されない**。
ローカル開発は HTTP なので、そのままだとログインが一切通らない。

**修正**：本番環境でだけ `Secure` を付けるようにし、設計書に明記。
あわせて、クッキーの有効期限をサーバー側のトークン有効期限（14日）から**計算して求める**ことにした。
両方に定数を書くと、片方だけ変えたときに「クッキーはあるのに 401 が返り続ける」状態になる。

**教訓**：**同じ意味を持つ値を2箇所に書かない。**

### 3-5. 登録済みのメールアドレスが分かってしまう

**問題**：パスワードのハッシュ化には Argon2 という**意図的に遅い**アルゴリズムを使う
（総当たり攻撃を遅くするため）。

素直に実装すると、こうなる。

- 存在するメールアドレス → パスワード検証が走る → **遅い**（数百ミリ秒）
- 存在しないメールアドレス → 検証せず即エラー → **速い**（数ミリ秒）

応答時間を測るだけで、**そのメールアドレスが登録済みかどうかが分かる**。
これを**タイミング攻撃**という。

**修正**：ユーザーが見つからない場合も、ダミーのハッシュに対して検証処理を1回走らせてから
エラーを返す。応答時間を揃える。

**教訓**：**「セキュリティのための処理」が、それ自体で情報を漏らすことがある。**

### 3-6. version が増えない場合がある

**問題**：楽観ロックの `version` は、SQLAlchemy が自動で増やしてくれる。
だが SQLAlchemy は「オブジェクトが実際に変更された」ときにしか UPDATE を発行しない。

同じタイトル・同じ本文で更新すると、**変更が無いので UPDATE が走らず、version も増えない**。
要件の「更新のたびに増加する」と厳密には食い違う。

**修正**：この挙動を**許容する**と明記し、理由を添えた。

> 値が変わっていない = 他のクライアントが持っているキャッシュを無効にする必要がない。
> つまり、衝突検出の正しさは損なわれない。

**教訓**：**要件と実装が食い違ったとき、必ずしも実装を直すとは限らない。
「要件が本当に守りたかったこと」が満たされているなら、食い違いを記録して許容する判断もある。**
大事なのは、**気づかないまま放置しない**こと。

### 3-7〜3-9. その他

- **絞り込み機能の前倒し**：本来は次のマイルストーンで作る予定だった機能の一部を、
  最小画面に必要なので前倒しした。**「うっかり入った」のか「意図して入れた」のか**を設計書に明記した
- **エラー応答の形式を揃える**：FastAPI が既定で返すバリデーションエラーは独自の形式なので、
  そのままだとアプリ独自のエラー形式と2種類が混在する。専用のハンドラを登録して揃える
- **クラスの置き場所を明記**：設計書のディレクトリ図に載っていないクラスがあったので追記

## 4. このレビューから取り出せる、3つの型

個別の修正を離れて、**次に設計するときに使える考え方**として3つ。

### 型1：「循環していないか」を疑う

修正1（最初のユーザーが作れない）と修正6（土台が上物を知る）は、
どちらも**循環**の問題だった。

- **状態の循環**：A になるには B が要り、B になるには A が要る
- **依存の循環**：A は B を知り、B は A を知る

設計を読み終えたら、こう問う。

> **「まっさらな状態から始めて、最初の1手は何か？」**

機能の要件を積み上げるだけでは、この穴は見えない。
**初期状態から順に、実際に手を動かす順番でなぞる**と見える。

### 型2：フレームワークの「デフォルト挙動」を疑う

修正3（422 になる）、修正5（間接 import も検出される）、修正7（commit がレスポンス後）は、
すべて**「フレームワークが親切にやってくれること」が、意図とズレていた**ケース。

新しいフレームワークを使うときに確認すべき3点。

1. **エラーはどのタイミングで、どの形で外に出るのか**
2. **書いたコードは、いつ実際に実行されるのか**（特に「後片付け」の処理）
3. **自動チェックのツールは、どこまでを検査対象にしているのか**

いずれも「動かしてみれば分かる」が、**設計の段階で間違えると作り直しになる**。
ドキュメントを引く価値があるのはこの3点。

### 型3：規約を仕組みに変える。そして仕組みを一度壊してみる

Reverb は「層をまたぐ依存の禁止」を CI で守る方針を採っている。これは正しい。
だが修正4で見たとおり、**設定が間違っていれば、検査は静かに何もしない**。

だから2段構えで考える。

1. 守りたいルールを、**人間の注意力ではなくツールに担わせる**
2. そのツールが**本当に働くことを、わざと違反して確かめる**

2 を飛ばすと、「守られているつもり」という**一番悪い状態**になる。

## 5. 用語集

| 用語 | 意味 |
|---|---|
| **認証（Authentication）** | 「あなたは誰か」を確かめること。失敗は HTTP 401 |
| **認可（Authorization）** | 「あなたは何をしてよいか」を決めること。失敗は HTTP 403 |
| **レイヤードアーキテクチャ** | Controller / Service / Repository のように役割で層を分け、依存を一方向に固定する設計 |
| **ORM** | データベースの行とプログラムのオブジェクトを対応づける道具。Reverb では SQLAlchemy |
| **Active Record** | モデル自身が保存の責務を持つパターン。Laravel の Eloquent |
| **Data Mapper / Unit of Work** | 変更を一旦セッションに溜め、まとめて反映するパターン。SQLAlchemy、JPA |
| **flush** | 溜まった変更を SQL としてデータベースへ送る（まだ確定しない） |
| **commit** | トランザクションを確定する。以後取り消せない |
| **楽観ロック** | 鍵をかけず、保存時に version 番号で衝突を検出する方式。衝突は HTTP 409 |
| **マイグレーション** | データベースの構造変更を、実行可能なファイルとして記録したもの。Reverb では Alembic |
| **依存性逆転の原則（DIP）** | 上位が必要とするインターフェースを、上位側に定義する。依存の向きを保つための原則 |
| **Protocol（Python）** | 「このメソッドを持つ何か」という型。実装側の宣言が不要（構造的部分型） |
| **import-linter** | モジュール間の依存ルールを検査する Python のツール。Java の ArchUnit に相当 |
| **CI** | コードを変更するたびに、テストや検査を自動実行する仕組み |
| **タイミング攻撃** | 処理時間の差から内部の情報を推測する攻撃手法 |
| **BFF（Backend For Frontend）** | フロントエンド専用の中継サーバー。Reverb では Next.js がクッキーとトークンの載せ替えだけを担う |
| **MCP** | AI エージェント（Claude Code）が外部サービスを操作するための接続規格 |

## 6. 今回のレビューの要約

設計書に対して16箇所の修正を入れた。内訳は次のとおり。

**そのままでは動かない・仕様を満たさないもの（7点）**

1. 最初のユーザーを作る経路が存在せず、誰もログインできなかった
2. デモアカウントが企画を作れてしまう権限の穴があった
3. 認証ヘッダーが無いときに 401 ではなく 422 が返る状態だった
4. 層の依存を検査するツールの設定が、そのままでは動かなかった
5. その検査ルールが、別の設計判断と正面衝突していた
6. 土台のコードが、その上に乗るモジュールに依存していた
7. データベースの確定処理が、レスポンス送信後に走る配置になっていた

**放置すると事故になるもの（9点）**

招待リンクによるオーナー降格、期限切れ招待の応答、テストのデータ分離、
ローカル環境のクッキー、メールアドレスの列挙、version の増加条件、その他3点。

**共通していること。**

16点のうち、**「機能が足りない」という指摘は1つも無い。**
すべて「**書いてある機能どうしを組み合わせたときに、想定と違う結果になる**」という種類の問題だった。

設計書は、機能を1つずつ書いているときは正しく見える。
**穴は、機能と機能の間、あるいは機能とフレームワークの間に開く。**
