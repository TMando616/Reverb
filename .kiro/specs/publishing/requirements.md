# requirements.md — publishing（チャネル変換・公開）

> **スペックの位置づけ**：Phase 1 の3本目。対応エピックは E4（チャネル変換）＋ E5（公開）。
> 対応マイルストーンは **M1（2026年10月末）と M3（2026年12月末）にまたがる。**
>
> - **M1（22h）**：Qiita 体裁への変換（12h）＋ Qiita API での公開と URL・外部 ID の記録（10h）。
>   M1 の判定 **「ネタを登録し、記事を書き、Qiita に公開できる」** の「公開できる」をこのスペックで通す
> - **M3（8h ＋ 残り）**：X の Web Intent、note・ポッドキャストの manual アダプタ、URL の貼り戻し
>
> 受け入れ条件には **【M1】／【M3】** を付ける。M1 の条件だけで「Qiita に公開できる」が閉じるように切ってある。

---

## 1. 目的

`content-pipeline` で書き終えた本文（`contents.body_md`）を、**チャネルごとの体裁に変換し、少ない手数で公開して、公開物として記録する。**

1. **チャネル変換** — 本文と変換プロファイル（構成ルール・禁則フレーズ・語尾・一人称）から、Claude API でチャネル向けの原稿を作る。原稿は人が直してから出す
2. **公開** — `ChannelAdapter` の3モード（auto / intent / manual）で公開し、`publications` に URL・外部 ID を残す

`publications` が残ることが、後続の `metrics`（日次の指標取得）の起点になる。**公開物が登録されなければ指標も取れない**（ADR-0005「影響」）。

## 3. 用語

| 用語 | 定義 |
|---|---|
| チャネル（channel） | 発信先。Qiita / X / note / ポッドキャスト。**企画をまたいで共通**の定義 |
| capabilities | チャネルの能力。`publish`（auto / intent / manual）・`format`（markdown / text）・`max_length` |
| 変換プロファイル | チャネルごとの書き方のルール（構成・禁則フレーズ・語尾・一人称）。変換時に LLM へ渡す |
| チャネル変換 | 本文とプロファイルから、あるチャネル向けの原稿を LLM で作ること |
| チャネル原稿（channel draft） | 変換結果を人が直したもの。**公開するのはこれ**で、`contents.body_md` そのものではない |
| 公開物（publication） | あるコンテンツを、あるチャネルへ公開した実体。URL・外部 ID・公開日時を持つ |
| 貼り戻し | intent / manual で公開したあと、公開先の URL を Reverb に入力して公開物にすること |
| 公開取消 | **公開物の登録を Reverb から外すこと。** 公開先の記事・投稿は消さない |

## 4. ロールと権限マトリクス

requirements-overview §4-2 に、本スペックの操作を足したもの。**判定は企画単位。**

| 操作 | owner | editor | reviewer | demo |
|---|:---:|:---:|:---:|:---:|
| チャネル原稿・変換履歴・公開物の閲覧 | ○ | ○ | ○ | ○ |
| チャネル変換の実行 | ○ | ○ | × | × |
| チャネル原稿の編集 | ○ | ○ | × | × |
| **公開（Qiita 投稿・更新／intent・manual の貼り戻し）** | **○** | × | × | × |
| **公開取消** | **○** | × | × | × |
| 変換プロファイルの閲覧 | ○ | ○ | ○ | ○ |
| 変換プロファイルの編集（M3・任意） | ○ | × | × | × |

**ユーザー単位の操作**（企画に属さない）：

| 操作 | 本人 | 他人 |
|---|:---:|:---:|
| 自分の Qiita アクセストークンの登録・差し替え・削除 | ○ | × |
| トークンの値の閲覧 | **×（登録後は誰も読めない）** | × |

demo アカウントはトークンを登録できない（読み取り専用の原則）。

## 5. ユーザーストーリーと受け入れ条件

### C1. チャネルと capabilities

**As a** 発信者
**I want** チャネルごとの「何ができるか」を1か所で決めておきたい
**So that** 画面とジョブに「Qiita なら〜」の分岐が散らばらない

- [ ] 【M1】チャネルは `publish`（auto / intent / manual）・`format`・`max_length` を capabilities として持つ（ADR-0005）
- [ ] 【M1】公開の分岐は capabilities を見て決まり、画面・Service にチャネル名での分岐を書かない
- [ ] 【M1】Qiita は `auto`。新規投稿と更新を API で行う
- [ ] 【M3】X は `intent`・`max_length = 280`、note・ポッドキャストは `manual`
- [ ] 【M1】チャネル一覧を API で取得できる（画面が capabilities からボタンを出し分けるため）

### C2. 変換プロファイル

**As a** 発信者
**I want** チャネルごとの書き分けルールを保存しておきたい
**So that** 毎回同じ指示を書かずに、自分の文体で変換される

- [ ] 【M1】チャネルごとに変換プロファイル（構成ルール・禁則フレーズ・語尾・一人称）を DB に保持する
- [ ] 【M1】Qiita のプロファイルは、既に言語化済みの Qiita 書き分けルールを初期値として持つ（シード）
- [ ] 【M3】note・X のプロファイルも同様に初期値を持つ
- [ ] 【M1】変換の実行履歴に、そのとき使ったプロファイルの内容（または版）が残る。プロファイルを後で変えても、過去の変換が何で作られたか分かる
- [ ] 【M3・任意】owner は画面からプロファイルを編集できる

### C3. チャネル変換

**As a** 発信者
**I want** 書き終えた本文を、ボタン1つでチャネルの体裁にしたい
**So that** 書き直す手間なく複数チャネルに出せる

- [ ] 【M1】owner / editor は、コンテンツとチャネルを指定して変換を実行できる
- [ ] 【M1】変換は Claude API に本文とプロファイルを渡して行う
- [ ] 【M1】**変換の実行はリクエストを待たせない。** 実行を受け付けた時点で応答し、状態（待機中／実行中／成功／失敗）を後から取得できる
- [ ] 【M1】画面は変換の状態を表示し、成功したら原稿を表示する（M1 は状態の取り直しでよい。SSE は M2）
- [ ] 【M1】失敗したとき（API エラー・タイムアウト・上限超過等）、理由が画面に出て、再実行できる
- [ ] 【M1】同じコンテンツ・同じチャネルで変換が実行中のあいだは、二重に実行できない（409）
- [ ] 【M1】変換の実行履歴（実行者・日時・チャネル・成否・失敗理由）が残り、一覧できる
- [ ] 【M1】reviewer / demo による変換の実行は 403
- [ ] 【M1】LLM の API キーはサーバーの環境変数で持ち、ブラウザ・レスポンス・ログに出さない

### C4. チャネル原稿

**As a** 発信者
**I want** 変換結果を直してから出したい
**So that** 生成結果をそのまま公開しない

- [ ] 【M1】変換が成功すると、そのコンテンツ・チャネルの**チャネル原稿**が作られる（タイトル・本文・チャネル固有の項目。Qiita ならタグ）
- [ ] 【M1】owner / editor はチャネル原稿を編集・保存できる。保存は楽観ロック（`version`）の対象で、他で更新されていれば 409
- [ ] 【M1】**再変換で手直しが黙って消えない。** 編集済みの原稿があるときに再変換すると、上書きしてよいか確認される（またはその場で上書きせず、新しい結果として並べる。方式は design で決める）
- [ ] 【M1】原稿が**変換元の本文より古い**（変換後に `contents.body_md` が更新された）ことが画面で分かる
- [ ] 【M1】公開するのはチャネル原稿であり、`contents.body_md` は変換・公開で書き換わらない
- [ ] 【M1】原稿のプレビューは HTML をサニタイズして描画する（content-pipeline C8 と同じ部品）
- [ ] 【M3】X の原稿は 280字を超えると警告され、超えたままでは Web Intent を開けない（文字の数え方は X の数え方に合わせ、design で決める）

### C5. Qiita のアクセストークン

**As a** owner
**I want** 自分の Qiita アカウントで投稿できるようにしたい
**So that** Reverb から直接 Qiita に出せる

- [ ] 【M1】ユーザーは自分の Qiita アクセストークンを登録・差し替え・削除できる
- [ ] 【M1】**トークンはアプリケーション層で暗号化して保存し、平文で保存しない**（requirements-overview §6-2）
- [ ] 【M1】登録後、トークンの値は API で返さない（登録済みかどうかと、どの Qiita ユーザーのものかだけ分かる）
- [ ] 【M1】登録時に Qiita へ問い合わせて有効性を確かめ、無効なら登録しない（422）
- [ ] 【M1】トークンが無い・無効になった状態で Qiita に公開しようとすると、理由が分かるエラーになり、登録画面へ誘導される
- [ ] 【M1】トークンはログ・例外メッセージ・エラーレスポンスに出ない
- [ ] 【M1】暗号化の鍵はサーバーの環境変数で持ち、DB と別に管理する

### C6. Qiita への公開（auto）

**As a** owner
**I want** ボタン1つで Qiita に投稿したい
**So that** 公開のたびにコピー＆ペーストしなくて済む

- [ ] 【M1】owner は Qiita のチャネル原稿を、API 経由で新規投稿できる
- [ ] 【M1】投稿の前に、Qiita の制約（タイトル必須・タグ数など。値は実装時に最新仕様で確認する）を検証し、満たさなければ送らずに理由を出す（422）
- [ ] 【M1】**限定共有で投稿できる**（公開範囲を選べる）。動作確認を一般公開せずに行うため
- [ ] 【M1】投稿に成功すると、公開物（チャネル・URL・外部 ID・公開日時・公開範囲）が記録される
- [ ] 【M1】投稿に成功すると、コンテンツは `公開済` に遷移する（既に `公開済` ならそのまま）
- [ ] 【M1】owner は公開済みの Qiita 記事を、チャネル原稿の内容で更新（再投稿）できる。更新日時が残る
- [ ] 【M1】**Qiita への送信が成功したのに記録に失敗する、を作らない**。送信と記録のどちらかで失敗したときに、二重投稿や記録漏れが起きない（方式は design で決める）
- [ ] 【M1】Qiita API のエラー（認証・レート制限・バリデーション・障害）は、種類ごとに理由が分かる形で返す
- [ ] 【M1】同じコンテンツを Qiita に二重に新規投稿できない（Qiita の公開物があれば「更新」になる）
- [ ] 【M1】editor / reviewer / demo による公開・更新は 403

### C7. intent / manual での公開と URL の貼り戻し

**As a** owner
**I want** API が無いチャネルでも、少ない手数で公開して記録したい
**So that** note や X に出したものも指標の対象にできる

- [ ] 【M3】X：ボタンを押すと、原稿が入った `x.com/intent/post?text=...` が新しいタブで開く
- [ ] 【M3】note・ポッドキャスト：ボタンを押すと原稿をクリップボードにコピーし、公開画面を新しいタブで開く
- [ ] 【M3】intent / manual は、公開後に URL を貼り戻すと公開物として登録され、コンテンツが `公開済` に遷移する
- [ ] 【M3】貼られた URL はチャネルごとの形式（ホスト名・パスの形）で検証し、合わなければ 422
- [ ] 【M3】同じ URL を二重に登録できない
- [ ] 【M3】貼り戻しは owner のみ（公開操作の一部として扱う）

### C8. 公開物と公開取消

**As a** 発信者
**I want** どのネタがどのチャネルに出たかを追いたい
**So that** 「あの記事、後でポッドキャストでも話したっけ」が分かる

- [ ] 【M1】1つのコンテンツに、チャネルごとの公開物を複数持てる（`contents 1 : n publications`）
- [ ] 【M1】コンテンツの画面で、そのコンテンツの公開物（チャネル・URL・公開日時）が分かる
- [ ] 【M1】企画の公開済み一覧で、コンテンツごとにどのチャネルへ出たかが分かる
- [ ] 【M1】owner は公開物の登録を取り消せる。**公開先の記事は消さない**ことが画面で明示される
- [ ] 【M1】公開取消は記録として残る（誰が・いつ取り消したか。後続の指標の扱いを判断できるように）
- [ ] 【M1】`公開済` からの遷移を解禁する（どこへ戻れるか、公開物がすべて取り消されたときに状態をどうするかは design で決める）
- [ ] 【M1】**`公開済` への遷移は公開操作からだけ起きる。** 汎用の状態遷移 API で `公開済` へは進めない（422）
- [ ] 【M1】他企画の公開物にはアクセスできない（ID を直接指定しても 404）

### C9. タグの提案（M3・任意）

**As a** 発信者
**I want** 本文からタグの候補を出してほしい
**So that** タグ付けの手間と表記ゆれが減る

- [ ] 【M3・任意】owner / editor は本文からタグ候補を提案させられる。候補は企画の既存タグを優先する
- [ ] 【M3・任意】候補は提案に留め、採用するまでコンテンツのタグは変わらない

### C10. テストと品質

- [ ] 【M1】Service 層のユニットテスト（認可分岐、二重実行の 409、Qiita の制約検証、公開物の記録、`公開済` への遷移、トークンの暗号化）
- [ ] 【M1】**Claude API・Qiita API はテストで実際に呼ばない。** 差し替え可能な境界（アダプタ・クライアント）を置き、fake で成功・失敗・タイムアウトを再現する
- [ ] 【M1】API の結合テスト（変換 → 原稿編集 → Qiita 投稿 → 公開物 → 更新、および 401 / 403 / 404 / 409 / 422 の各系統）
- [ ] 【M1】新しい Service も HTTP に依存せず、MCP / ジョブから同じ認可で呼べる（`lint-imports` が緑）
- [ ] 【M1】`ruff` / `mypy` / `lint-imports` / フロントの `lint` / `tsc` / `build` が CI で緑
- [ ] 【M1】手動確認：**ネタを書く → Qiita 体裁に変換 → 原稿を直す → 限定共有で投稿 → URL が記録され `公開済` になる → 原稿を直して更新**が通る（M1 の判定）

## 6. 非機能・制約

- **依存方向**：`Controller → Service → Repository`（ADR-0009）。チャネルアダプタ・LLM クライアントは **Service から呼ぶ**。Controller から直接呼ばない
- **認可**：本スペックで足すすべての操作を、Service 冒頭の明示チェックで判定する。**公開は owner のみ**を画面で隠すだけにしない
- **外部 API の境界**：Claude API・Qiita API の呼び出しは差し替え可能な境界の向こうに置く（テストと、M2 のジョブ基盤への載せ替えのため）
- **Claude API**：コードを書く前に `/claude-api` スキルを読む（CLAUDE.md）。モデル ID・パラメータを記憶で書かない
- **Qiita API・X の Web Intent**：実装時に最新仕様を確認する（requirements-overview §7）
- **秘密情報**：Qiita トークンは暗号化保存。LLM の API キーと暗号化の鍵は環境変数。どれもログ・レスポンスに出さない
- **外部への送信**：変換時、本文（共同編集者が書いた部分を含む）を Anthropic の API に送る。招待制で利用者は限られるが、**企画のメンバーに分かる形で画面に明記する**（下記「個人情報の扱い」）
- **フロント**：BFF 経由（ADR-0014）。チャネル原稿の編集中バッファはクライアント状態（frontend.md §2）
- **コスト**：LLM の呼び出しは owner / editor の明示操作でだけ起きる。自動の再試行で何度も呼ばない
