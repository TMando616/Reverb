# requirements.md — content-pipeline（ネタ管理・執筆）

> **スペックの位置づけ**：Phase 1 の2本目。対応エピックは E1（ネタの在庫管理）の残り ＋ E2（執筆）。
> 対応マイルストーンは **M1（2026年10月末・「縦に1本通す」）** のうち、エディタ（30h）とタグ・カンバン（10h）の部分。
> M1 の判定 **「ネタを登録し、記事を書き、Qiita に公開できる」** のうち、**「書く」までをこのスペックで通す。** 公開は `publishing`。

---

## 1. 目的

foundation で作った「コンテンツの器」に、**ネタを溜めて眺める道具**と**書く道具**を載せる。

1. **ネタの在庫管理** — タグ（多対多）、状態別のカンバン、タグ・状態・キーワードでの絞り込み、元ノートのパス保持
2. **執筆** — 既製の Markdown エディタ、自動保存、保存ごとのリビジョン記録と復元、プレビュー、文字数表示

これが動けば、`publishing` は「書き終えた本文を Qiita 体裁に変換して投げる」ことだけに集中できる。

## 3. 用語

| 用語 | 定義 |
|---|---|
| タグ（tag） | コンテンツに付けるラベル。**企画ごとに持つ**（企画をまたいで共有しない） |
| カンバン | 6状態をそれぞれ列にし、コンテンツをカードとして並べた一覧画面 |
| リビジョン（revision） | ある時点の本文（`title` / `body_md`）のスナップショット。追記専用 |
| 自動保存 | ユーザーの明示操作なしに、編集中の本文をサーバーへ保存すること |
| 編集中バッファ | エディタ上の、まだ保存していない本文。**クライアント状態**（frontend.md §2） |
| 元ノートのパス（source_note_path） | ネタの出どころである Obsidian ノートの、Vault からの相対パス。**文字列として保持するだけ** |

## 4. ロールと権限マトリクス

foundation の権限マトリクス（`foundation/requirements.md` §4）に、本スペックの操作を足したもの。**判定は企画単位。**

| 操作 | owner | editor | reviewer | demo |
|---|:---:|:---:|:---:|:---:|
| カンバン・一覧・絞り込みの閲覧 | ○ | ○ | ○ | ○ |
| タグの閲覧 | ○ | ○ | ○ | ○ |
| タグの作成・改名・削除 | ○ | ○ | × | × |
| コンテンツへのタグ付け・外し | ○ | ○ | × | × |
| 本文の編集・自動保存 | ○ | ○ | × | × |
| リビジョンの一覧・閲覧 | ○ | ○ | ○ | ○ |
| リビジョンの復元 | ○ | ○ | × | × |
| `source_note_path` の設定・変更 | ○ | ○ | × | × |
| カンバン上からの状態遷移 | ○ | ○ | × | × |

reviewer がリビジョンを閲覧できるのは、レビュー（`collaboration`）で「前の版と比べてどう変わったか」を見る必要があるため。

## 5. ユーザーストーリーと受け入れ条件

### C1. タグ

**As a** 発信者
**I want** ネタに複数のタグを付けたい
**So that** テーマ別にネタを探せて、後でタグ別の反応を比較できる（E7 の土台）

- [x] owner / editor は企画内にタグを作成できる（名前必須）
- [x] 同じ企画内で同名のタグは作れない（大文字小文字・前後の空白の扱いは design で決める）
- [x] タグは企画に属し、別の企画のタグをコンテンツに付けることはできない
- [x] owner / editor はタグを改名でき、改名は付与済みのコンテンツすべてに反映される
- [x] owner / editor はタグを削除でき、削除するとすべてのコンテンツから外れる（コンテンツ自体は消えない）
- [x] 1つのコンテンツに複数のタグを付けられ、1つのタグを複数のコンテンツに付けられる（多対多）
- [x] 同じコンテンツに同じタグを二重に付けることはできない
- [x] コンテンツの取得・一覧で、付いているタグが分かる
- [x] reviewer / demo によるタグの作成・改名・削除・付け外しは 403 で拒否される

### C2. カンバン

**As a** 発信者
**I want** ネタを状態別の列で一覧したい
**So that** どれが眠っていて、どれが公開間近かが一目で分かる

- [x] 企画のコンテンツが、6状態を列にしたカンバンで表示される（列の並び順は状態遷移の流れに沿う）
- [x] 各カードにタイトル・タグ・最終更新日時が表示される
- [x] owner / editor はカンバン上から状態を変更できる（操作方法はドラッグ＆ドロップかメニューかを design で決める）
- [x] 遷移できない先は、画面上で選べないか、選んだ時点で分かる（**UX のため。防御は foundation の API の 422**）
- [x] 状態変更が API で拒否された場合（422 / 409 / 403）、カードは元の列に戻り、理由が表示される
- [x] reviewer / demo には状態変更の操作が出ない（API 側でも 403 になることは foundation で担保済み）
- [x] カードからコンテンツの編集画面（reviewer / demo は閲覧画面）へ移動できる
- [x] カンバンから新しいネタを登録できる（タイトル・タグ・メモ）

### C3. 絞り込み

**As a** 発信者
**I want** タグ・状態・キーワードでネタを絞り込みたい
**So that** ネタが増えても目的のものにすぐ辿り着ける

- [x] コンテンツ一覧 API は、タグ・状態・キーワードで絞り込める
- [x] タグは複数指定でき、指定したタグを**すべて**持つものに絞り込む（AND。OR が要るかは使ってから判断する）
- [x] 状態は複数指定できる
- [x] キーワードはタイトルと本文の部分一致で絞り込む
- [x] 条件は組み合わせられる（タグ AND 状態 AND キーワード）
- [x] 絞り込みは企画スコープの中だけで効く（他企画のコンテンツは出ない）
- [x] 一覧 API は本文全体を返さない（カンバンの表示に不要な本文でレスポンスを膨らませない）
- [x] 画面の絞り込み条件は URL に残り、リロード・共有しても同じ結果になる

### C4. 元ノートのパス

**As a** 発信者
**I want** ネタの元になった Obsidian ノートのパスを残したい
**So that** 「あの断片メモがこの記事になった」を後から辿れる

- [x] コンテンツは任意項目として `source_note_path` を持てる
- [x] 作成時・更新時に owner / editor が設定・変更・削除できる
- [x] パスは Vault からの相対パスとして保持し、絶対パス・`..` を含むものは 422 で拒否する
- [x] **サービスはこのパスのファイルを読まない・存在確認もしない**（Vault に到達できないため）
- [x] 編集画面・閲覧画面で元ノートのパスが表示される
- [x] 将来 MCP（`create_content`）から同じ Service を通して設定できる形になっている

### C5. エディタと編集画面

**As a** 発信者
**I want** アプリの中で Markdown の記事を書きたい
**So that** ネタから公開までを1箇所で完結できる

- [x] **既製の Markdown エディタ**を組み込んで本文を編集できる（**自作しない**。選定は ADR に残す）
- [x] 編集画面でタイトルと本文を編集できる
- [x] 編集画面からタグと `source_note_path` を編集できる
- [x] エディタはクライアントコンポーネントに閉じ、ページの初期データ取得はサーバー側で行う（frontend.md §3）
- [x] 編集中バッファはクライアント状態として持ち、サーバー状態のキャッシュを直接書き換えない（frontend.md §2）
- [x] reviewer / demo が開くと、編集できない閲覧画面になる（API 側でも 403）

### C6. 自動保存と競合検出

**As a** 発信者
**I want** 書いた内容が自動で保存されてほしい
**So that** 保存し忘れやタブの閉じ忘れで原稿を失わない

- [x] 編集が止まってから一定時間で自動保存される（間隔は design で決める）
- [x] 手動でも保存できる（ショートカットキーかボタン）
- [x] 保存状態（未保存の変更あり／保存中／保存済み／保存失敗）が画面に表示される
- [x] 保存は読み込み時の `version` を添えて送り、**他で更新されていれば 409 で拒否される**（foundation の楽観ロック）
- [x] 409 を受けたら自動保存を止め、編集中バッファを失わずに「他で更新された」ことを表示する（差分提示は `collaboration`）
- [x] 保存失敗（通信エラー等）のとき、編集中バッファは失われず、再試行できる
- [x] 未保存の変更があるままページを離れようとすると警告される
- [x] 本文が変わっていない保存は、`version` を進めず、リビジョンも作らない

### C7. リビジョン

**As a** 発信者
**I want** 過去の版を見返して、必要なら戻したい
**So that** 書き直して失敗しても前の状態に戻れる

- [x] **本文（タイトル・本文）が変わる保存のたびに、リビジョンが1件記録される**（自動保存・手動保存を問わない）
- [x] リビジョンには、保存した人・保存日時・その時点のタイトルと本文全体が残る
- [x] リビジョンは追記専用で、更新・削除の API を持たない
- [x] 1コンテンツのリビジョンを新しい順に一覧できる（一覧は本文全体を返さない）
- [x] 任意のリビジョンの本文を閲覧できる
- [x] owner / editor は任意のリビジョンへ復元できる
- [x] **復元は履歴を巻き戻さず、「その版の内容で新しく保存する」として新しいリビジョンを1件作る**
- [x] 復元も楽観ロック（`version`）の対象で、古い `version` での復元は 409 になる
- [x] 他企画のコンテンツのリビジョンにはアクセスできない（ID を直接指定しても 403 / 404）
- [x] 状態遷移・タグの付け外し・`source_note_path` の変更ではリビジョンを作らない（本文の履歴と混ぜない。状態遷移は foundation の `content_status_transitions` に残る）

### C8. プレビューと文字数

**As a** 発信者
**I want** 書いている記事の見た目と長さを確認したい
**So that** 公開前に体裁と分量を判断できる

- [x] 本文の Markdown をプレビュー表示できる（エディタと並べるか切り替えるかは design で決める）
- [x] **プレビューは HTML をサニタイズしてから描画する**（本文中の `<script>` 等を実行させない。reviewer / demo も同じ画面を見るため）
- [x] 文字数が編集に合わせてリアルタイムに表示される
- [x] 文字数の数え方（Markdown 記法・コードブロックを含めるか、改行・空白の扱い）を design で決め、画面上で分かるようにする
- [x] 閲覧画面（reviewer / demo）でもプレビューと文字数を見られる

### C9. テストと品質

- [x] Service 層のユニットテストがある（タグの企画スコープ、絞り込み条件、リビジョン記録の有無、復元、各操作の認可分岐）
- [x] Repository 層のユニットテストがある（タグ AND 絞り込み、キーワード検索、企画スコープ）
- [x] API の結合テストがある（タグ付け → 絞り込み → 本文保存 → リビジョン一覧 → 復元、および 401 / 403 / 404 / 409 / 422 の各系統）
- [x] 新しい Service も HTTP に依存せず、MCP / ジョブから同じ認可で呼べる（`lint-imports` が緑）
- [x] `ruff` / `mypy` / `lint-imports` / フロントの `lint` / `tsc` / `build` が CI で緑になる

## 6. 非機能・制約

- **依存方向**：`Controller → Service → Repository`（ADR-0009）。タグ・リビジョンも `modules/{domain}/` の層構造に従う
- **認可**：本スペックで足すすべての操作を、Service 冒頭の明示チェックで判定する（foundation design.md §5-2 と同じ形）
- **エディタ**：既製品を組み込むだけ。自作しない（tech.md）
- **フロントの状態**：サーバー状態／クライアント状態を混ぜない。編集中バッファはサーバーへ送るまで外に出さない（frontend.md §2）
- **セキュリティ**：Markdown プレビューはサニタイズ必須。ブラウザから FastAPI を直接叩かない（BFF 経由・ADR-0014）
- **性能の目安**：1企画あたりコンテンツ数百件・1コンテンツあたりリビジョン数百件で、カンバン表示と絞り込みが体感で待たない程度（厳密な目標値は持たない。50万行の実測は `metrics` の担当）
- **Obsidian**：サービスから Vault に一切アクセスしない。`source_note_path` は文字列として保持するだけ
