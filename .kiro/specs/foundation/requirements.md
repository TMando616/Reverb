# requirements.md — foundation（認証・認可・コンテンツ土台）

> **スペックの位置づけ**：Phase 1 の1本目。対応エピックは E9（認証・認可）＋ E1 / E3 の M0 スライス。
> 対応マイルストーンは **M0（2026年9月末・「土台」）**。
> 判定基準は `docs/requirements-overview.md` §12 M0：**ログインして、企画を作り、ネタを登録して状態を動かせる。**

---

## 1. 目的

Reverb の全機能が乗る土台を最初に据える。具体的には次の3つ。

1. **認証** — 招待されたユーザーだけがログインできる。セッションはトークンで管理する
2. **認可** — 企画（project）を共有単位とし、owner / editor / reviewer の3ロールを **API 層で** 強制する
3. **コンテンツの器** — ネタ（content）を企画配下で CRUD でき、定義された6状態の間だけ遷移できる

この3つが動けば、以降のスペック（執筆・公開・指標・レビュー・MCP）はすべてこの上に機能を足すだけになる。

## 3. 用語

| 用語 | 定義 |
|---|---|
| ユーザー（user） | ログインできる主体。招待されて初めて存在する |
| 企画（project） | コンテンツをまとめるシリーズ。**共有とロールの単位** |
| メンバーシップ（project_member） | あるユーザーの、ある企画での役割（owner / editor / reviewer） |
| コンテンツ（content） | 受信箱から公開まで一貫して状態遷移する単位。記事1本に相当 |
| 状態（status） | コンテンツのライフサイクル位置。6値 |
| デモ閲覧者（demo） | 読み取り専用の共有アカウント。ロールとは別軸の制約 |

## 5. ユーザーストーリーと受け入れ条件

チェックの根拠は `acceptance-trace.md`（条件 → テストの対応表）にある。
**未チェックの2件は「満たしていない」ではなく、テストではなく仕組みで守っているもの**：
認可が Service にあることは `.importlinter` の契約で、コンテンツが企画に属することは
`contents.project_id` の NOT NULL + FK で担保する（2026-09-28）。


### F1. ログインとセッション

**As a** 招待済みのユーザー
**I want** メールアドレスとパスワードでログインしたい
**So that** 自分の企画とコンテンツにアクセスできる

- [x] 正しい email + password でログインでき、セッショントークンが発行される
- [x] 誤った資格情報では 401 が返り、トークンは発行されない
- [x] パスワードはハッシュ化して保存される（平文で保存しない）
- [x] 発行されたトークンを付与したリクエストで、保護された API にアクセスできる
- [x] トークンが無い／不正／期限切れのリクエストは 401 で拒否される
- [x] ログアウトすると、そのトークンは以後 401 になる
- [x] トークンには有効期限がある

### F2. 招待制ユーザー管理

**As a** 企画の owner
**I want** メンバーを招待して役割を割り当てたい
**So that** 共同編集者・レビュアーと企画を共有できる

- [x] **一般ユーザーの自己登録エンドポイントは存在しない**（サインアップ画面・API を持たない）
- [x] owner は企画に対して招待を発行できる（招待リンク、または宛先メールアドレス指定）
- [x] 招待発行時に owner / editor / reviewer のいずれかを指定する
- [x] 招待を受諾したユーザーは、その企画の `project_member` として指定ロールで追加される
- [x] 未登録の宛先を招待した場合、受諾フローの中でパスワードを設定してユーザーが作られる
- [x] 招待には有効期限があり、期限切れの招待は受諾できない
- [x] 同一企画・同一ユーザーに対する重複メンバーシップは作られない
- [x] owner はメンバーのロールを変更でき、メンバーを除名できる
- [x] **企画から最後の owner を除名／降格することはできない**
- [x] owner 以外が招待・ロール変更・除名の API を呼ぶと 403 で拒否される

### F3. デモアカウント

**As a** プロジェクトのオーナー
**I want** 読み取り専用のデモアカウントを用意したい
**So that** URL を渡すだけで初見の人にプロダクトを触ってもらえる

- [x] 読み取り専用のデモアカウントでログインできる
- [x] デモアカウントは、参加している企画とそのコンテンツ・指標を閲覧できる
- [x] デモアカウントによる作成・更新・削除・状態遷移・招待の API 呼び出しは、ロールに関わらず 403 で拒否される
- [x] デモアカウントであることが、認可判定の中で識別できる

### F4. 企画とメンバー

**As a** ユーザー
**I want** 企画を作って自分のコンテンツをまとめたい
**So that** シリーズ単位で共有と権限を管理できる

- [x] ユーザーは企画を作成でき、作成者は自動的にその企画の owner になる
- [x] ユーザーは、自分がメンバーである企画のみ一覧・取得できる
- [x] メンバーでない企画の取得は 403（または存在を隠す 404）で拒否される
- [x] 企画の取得時に、自分のロールが分かる

### F5. 認可の API 層強制

**As a** プロジェクトのオーナー
**I want** 権限のない操作をサーバー側で必ず拒否したい
**So that** 画面で隠しているだけの状態を作らず、MCP やジョブ経由でも同じ防御が効く

- [x] §4 の権限マトリクスに反する操作は、すべて API 層（Service）で拒否される
- [ ] 認可判定は Controller ではなく Service に置かれる（HTTP に依存しない）
- [x] 同じ Service を HTTP 以外（MCP / ジョブ）から呼んでも、同一の認可ロジックが通る
- [x] 認可拒否は 403、認証切れは 401 と、明確に区別される
- [x] リソースの所属企画を無視した横断アクセス（他企画の content_id 指定など）が拒否される
- [x] 認可の判定単位が「共有単位（企画）＋リソース単位（コンテンツ）」の両方で機能する

### F6. コンテンツの CRUD

**As a** 発信者
**I want** 思いついたネタを登録・編集・削除したい
**So that** ネタを在庫として1箇所で管理できる

- [x] owner / editor は、自分がメンバーである企画配下にコンテンツを作成できる（title 必須、body_md 任意、初期 status は `受信箱`）
- [ ] コンテンツは必ずいずれかの企画に属する
- [x] 企画のメンバーは、その企画のコンテンツを一覧・取得できる
- [x] owner / editor は title / body_md を更新できる
- [x] reviewer / demo による作成・更新・削除は 403 で拒否される
- [x] owner / editor はコンテンツを削除できる（論理削除か物理削除かは design で決める）
- [x] コンテンツは楽観ロック用の `version` を持ち、更新のたびに増加する
- [x] 古い `version` を指定した更新は 409（競合）で拒否される

### F7. コンテンツの状態遷移

**As a** 発信者
**I want** ネタの進行状態を段階的に動かしたい
**So that** どれが眠っていて、どれが公開間近かが分かる

- [x] status は次の6値をとる：`受信箱` → `採用` → `執筆中` → `レビュー中` → `公開済` → `見送り`
- [x] 状態遷移は専用の API で行い、title / body_md の更新とは分離されている
- [x] **定義されていない遷移は 422（不正遷移）で拒否される**（例：`受信箱` から直接 `公開済` へは飛べない）
- [x] 許可される遷移は次のとおり（design.md で最終確定する）：

  | 現在 | 遷移できる先 |
  |---|---|
  | `受信箱` | `採用`, `見送り` |
  | `採用` | `執筆中`, `受信箱`, `見送り` |
  | `執筆中` | `レビュー中`, `採用`, `見送り` |
  | `レビュー中` | `執筆中`, `見送り`（`公開済` への遷移は `publishing` スペックで解禁する） |
  | `公開済` | （foundation では遷移元にしない） |
  | `見送り` | `受信箱` |

- [x] 状態遷移の権限は owner / editor のみ（reviewer / demo は 403）
- [x] 遷移は監査可能な形で記録される（誰が・いつ・どの状態からどの状態へ）
- [x] 同時実行で二重に遷移が走っても、不正な状態にならない（`version` による保護）

### F8. レイヤー構成と依存契約

**As a** 開発者（＝自分）
**I want** 層をまたぐ依存を CI で検出したい
**So that** 「気をつける」ではなく仕組みで ADR-0009 のレイヤー構成を守れる

- [x] `backend/` が `structure.md` のディレクトリ構造に沿って作られる（`modules/{domain}/router.py` / `service.py` / `repository.py` …）
- [x] `.importlinter` に「Controller → Service → Repository の一方向」を表す契約が定義される
- [x] `lint-imports` が CI で実行され、層をまたぐ import があるとビルドが落ちる
- [x] Service 層に FastAPI の `Request` / `Response` が import されていない
- [x] DI は FastAPI の `Depends` に寄せられており、Router が Service を直接 `import` して組み立てていない

### F9. テストと API 仕様

- [x] Service 層のユニットテストがある（認可分岐・状態遷移の可否を網羅）
- [x] Repository 層のユニットテストがある（企画スコープでの絞り込み）
- [x] API エンドポイントの結合テストがある（ログイン → 企画作成 → コンテンツ登録 → 状態遷移、および 401 / 403 / 409 / 422 の各系統）
- [x] OpenAPI スキーマが自動生成され、参照できる
- [x] `ruff` / `mypy` / `lint-imports` が CI で緑になる

## 6. 非機能・制約

- **セキュリティ**：パスワードはハッシュ化。権限チェックは API 層で拒否する（画面で隠すだけにしない）。自己登録は無効
- **依存方向**：`Controller → Service → Repository`。下位が上位を参照しない（ADR-0009）
- **Service の独立性**：Service は Request / Response を知らない。MCP・ジョブから呼べる状態を保つ
- **ORM**：SQLAlchemy 2.0 / SQLModel / Tortoise のいずれか（**ADR-0002 で決定してから design.md に入る**）。マイグレーションは Alembic
- **DB**：PostgreSQL
