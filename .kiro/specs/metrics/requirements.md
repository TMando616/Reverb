# requirements.md — metrics（指標の収集・分析）

> **スペックの位置づけ**：Phase 1 の4本目。対応エピックは E6（指標の収集）＋ E7（分析）。
> 対応マイルストーンは **M2（2026年11月末）が中心で、性能実測だけ M3（2026年12月末）。**
>
> - **M2（50h）**：指標取得ジョブ（リトライ・レート制限・SSE 進捗・ポッドキャスト RSS 取り込み）30h ＋ ダッシュボードと分析クエリ 20h。
>   M2 の判定 **「1週間放置して指標が溜まっている」** をこのスペックで通す
> - **M3**：50万行をシードした性能実測と、README への Before/After 掲載
>
> 受け入れ条件には **【M2】／【M3】** を付ける。
> 分析（E7）のうち、**削る順番の1番目「分析画面をダッシュボードに統合（−15h）」**（requirements-overview §11）を発動したときに扱いが変わるものには **【統合時も残す】／【統合時に落とせる】** を付ける。発動するかは11月中旬に判断する（§12「遅れていた場合の打ち手」）。

---

## 1. 目的

**公開後の数字を、手を動かさずに日次で溜め続け、何が伸びて何が伸びなかったかを見られるようにする。**

1. **収集** — 公開物（`publications`）ごとに、1日1回の指標スナップショットを残す。自動で取れるもの（Qiita）はジョブで取り、取れないもの（X・note・Spotify）は手で入れる
2. **分析** — 溜まったスナップショットから、直近の推移・伸びている記事・公開後 N 日の伸び方・タグ別の反応などを出す

各プラットフォームは「現在値」しか見せない。**日次で取り続けない限り推移は二度と復元できない**（product.md「解く課題」）。だから収集は M2 の早い段階で動かし始め、分析はデータが溜まりながら作る。

### 2-2. このスペックに含まない

| 除外するもの | 理由 / 引き継ぎ先 |
|---|---|
| **note の公開ページからの指標取得** | 公開 API が無く、ページ構造の変化で壊れやすい。規約の確認も要る。Phase 1 は手入力だけにし、Phase 2 で検討する |
| X API・Spotify の API による指標取得 | X は Phase 2（product.md）。Spotify for Creators は公開 API が無い。どちらも手入力 |

| 指標のエクスポート（CSV 等） | 要件に無い。必要なら Phase 2 |
| 通知（伸びたらメール等） | 要件に無い。Phase 2 |
| MCP の指標ツール | `mcp-server`（M3）。本スペックは Service を HTTP に依存させない形にするまで |

## 3. 用語

| 用語 | 定義 |
|---|---|
| 指標（metric） | 公開物に対する反応の数値。閲覧数・いいね（LGTM・スキ）・ストック・コメント・再生数・インプレッションなど。チャネルごとに取れるものが違う |
| スナップショット | ある公開物の、ある日の指標の値。**公開物×日付で1レコード** |
| 対象日 | スナップショットの日付。**日本時間（JST）の日付**で数える |
| 欠測 | 取得できなかった日。レコードが無い状態として残す（0 で埋めない） |
| 取得ジョブ | 指標を取る・RSS を読むなどの非同期処理の1回分。`job_runs` に記録される |
| 定期実行 | 1日1回、自動で取得ジョブを投入すること |
| 手動実行 | owner が画面から取得ジョブを投入すること |
| 公開後 N 日 | 公開日を0日目とした相対日数。公開日の違う記事同士を同じ横軸で比べるために使う |
| コホート | 公開月が同じ公開物のまとまり |

## 4. ロールと権限マトリクス

requirements-overview §4-2 に、本スペックの操作を足したもの。**判定は企画単位。**

| 操作 | owner | editor | reviewer | demo |
|---|:---:|:---:|:---:|:---:|
| 指標・ダッシュボード・分析の閲覧 | ○ | ○ | ○ | ○ |
| ジョブの実行履歴の閲覧 | ○ | ○ | ○ | ○ |
| 指標の手入力・修正 | ○ | ○ | × | × |
| 取得ジョブの手動実行・再実行 | ○ | × | × | × |
| ポッドキャスト RSS の登録・変更・削除 | ○ | × | × | × |

- 手動実行を owner に限るのは、外部 API を呼ぶ操作で、Qiita は公開した人のトークンを使うため（公開と同じ扱い）
- RSS の登録を owner に限るのは、登録すると企画にコンテンツと公開物が作られる＝公開の操作に当たるため

## 5. ユーザーストーリーと受け入れ条件

### S1. 指標スナップショット

**As a** 発信者
**I want** 公開物ごとの数字を日ごとに残したい
**So that** 「公開後3日で伸びた／じわじわ伸びた」を後から区別できる

- [ ] 【M2】指標は**公開物×対象日で1レコード**として記録される
- [ ] 【M2】**同じ公開物・同じ対象日の再取得は上書き**され、レコードは増えない
- [ ] 【M2】対象日は日本時間の日付で数える
- [ ] 【M2】各値には、自動で取ったか手で入れたか（取得元）が残る
- [ ] 【M2】チャネルごとに取れない指標は「値なし」として持ち、0 と区別する
- [ ] 【M2】取得できなかった日は欠測として残り、0 で埋めない
- [ ] 【M2】公開取消された公開物は、取消以降は自動取得の対象から外れる。取消前のスナップショットは消えずに残る
- [ ] 【M2】他企画の公開物のスナップショットにはアクセスできない（ID を直接指定しても 404）

### S2. 日次の自動取得（Qiita）

**As a** 発信者
**I want** 公開後の数字が自動で溜まってほしい
**So that** 手を動かさずに推移が残る

- [ ] 【M2】**1日1回、`metrics = auto` のチャネルの全公開物について指標を取る**（M2 では Qiita）
- [ ] 【M2】取得は**キューを介した非同期ジョブ**として実行され、API のリクエストを待たせない
- [ ] 【M2】Qiita からは、API で取れる指標（LGTM・ストック、取れるなら閲覧数）を取る。取れる項目は実装時に最新仕様で確かめる
- [ ] 【M2】Qiita の取得には、その公開物を公開したユーザーのトークンを使う。トークンが無い・無効なら、その公開物はエラーとして記録し、他の公開物の取得は止めない
- [ ] 【M2】**同じ対象日の定期実行は、プロセスが複数あっても1回しか投入されない**（ADR-0013）
- [ ] 【M2】ワーカーが止まっていて定期実行の時刻を過ぎた場合、起動後にその日の分が投入される（前日以前の分はさかのぼらない）
- [ ] 【M2】チャネルの分岐は capabilities（`metrics`）を見て決まり、チャネル名での分岐を Service・ジョブに書かない（publishing C1 と同じ）

### S3. リトライ・レート制限

**As a** 発信者
**I want** 外部 API が一時的に落ちても欠測にならないでほしい
**So that** 日次の推移に穴が空かない

- [ ] 【M2】**失敗した取得は、間隔をあけて自動でリトライされる**（間隔は回を追うごとに延びる）
- [ ] 【M2】**リトライ上限に達したら失敗として確定し、エラー（種類・メッセージ・時刻）が記録される**
- [ ] 【M2】認証エラー・対象が存在しない（記事が消された等）のように、繰り返しても直らない失敗はリトライしない
- [ ] 【M2】外部 API のレート制限を超えないよう、チャネルごとに実行間隔を制御する
- [ ] 【M2】外部 API からレート制限の応答が来たら、指定された時刻（無ければ一定時間）まで待ってから再開する
- [ ] 【M2】取得の途中でプロセスが落ちても、ジョブは失われず、回収されて再実行される（ADR-0017 と同じ回収の仕組み）

### S4. ジョブの実行履歴と手動実行

**As a** owner
**I want** 取得がちゃんと回っているか、失敗していないかを確かめたい
**So that** 欠測に気づいて手を打てる

- [ ] 【M2】ジョブの実行状況（待機中／実行中／成功／失敗）とエラー履歴を、企画ごとに画面で一覧できる
- [ ] 【M2】1回の実行で何件の公開物を取り、何件失敗したかが分かる
- [ ] 【M2】owner は画面から取得ジョブを手動で実行できる
- [ ] 【M2】owner は失敗したジョブを再実行できる。**失敗した記録は書き換えずに残り**、再実行は新しい実行として記録される
- [ ] 【M2】同じ企画で取得ジョブが待機中・実行中のあいだは、二重に手動実行できない（409）
- [ ] 【M2】editor / reviewer / demo による手動実行・再実行は 403

### S5. 手動実行の進捗（SSE）

**As a** owner
**I want** 手動で実行したときに、進み具合をその場で見たい
**So that** 終わるまで画面を何度も読み直さなくて済む

- [ ] 【M2】**手動実行したときは、進捗（何件中何件・成功／失敗）がリアルタイムで画面に流れる**（SSE・ADR-0006）
- [ ] 【M2】接続が切れても、再接続すると現在の状態から表示が続く
- [ ] 【M2】ジョブが終わると、ストリームは完了を伝えて閉じる
- [ ] 【M2】SSE もほかの API と同じく、BFF を経由し認可を通す。他企画のジョブの進捗は購読できない（404）
- [ ] 【M2】進捗の正は `job_runs` の状態で、SSE が無くても状態の取り直しで同じ情報が得られる

### S6. ポッドキャスト RSS の取り込み

**As a** 発信者
**I want** ポッドキャストの新エピソードを、配信するだけで公開物にしたい
**So that** ポッドキャストも記事と同じ器で追える

- [ ] 【M2】owner は企画にポッドキャストの RSS の URL を登録・変更・削除できる
- [ ] 【M2】登録時に RSS を読んで形式を確かめ、読めなければ登録しない（422）
- [ ] 【M2】RSS は定期実行で読まれ、**新しいエピソードは、エピソードごとにコンテンツ（`公開済`・タイトルはエピソード名）と公開物（ポッドキャスト・URL・公開日時）として自動で登録される**
- [ ] 【M2】登録した時点で RSS にある既存のエピソードも取り込む（指標はさかのぼらない）
- [ ] 【M2】**同じエピソードは二度登録されない**（エピソードの識別子で判定する）
- [ ] 【M2】公開取消したエピソードは、次の取り込みで復活しない
- [ ] 【M2】RSS の取り込みもジョブとして実行履歴に残り、失敗時はリトライされる
- [ ] 【M2】RSS 取り込みで作られるコンテンツ・公開物は、誰の操作によるものか（RSS を登録した owner）が記録される
- [ ] 【M2・任意】取り込まれたエピソードを、既存のネタ（コンテンツ）にまとめ直せる（「あの記事を後でポッドキャストでも話した」を1本のネタにする）

### S7. 指標の手入力

**As a** 発信者
**I want** 自動で取れない数字も同じ場所に残したい
**So that** X・note・Spotify の反応も横断で比べられる

- [ ] 【M2】owner / editor は、公開物と対象日を指定して指標を手で入力できる
- [ ] 【M2】入力できる指標はチャネルごとに決まっている（X ならインプレッション、Spotify なら再生数など。チャネルの定義側に持つ）
- [ ] 【M2】同じ公開物・同じ対象日への入力は上書きになる
- [ ] 【M2】**自動取得した値は手入力で上書きしない**（同じ指標を両方から入れられない。どちらの値か分からなくなるため）
- [ ] 【M2】未来の日付・公開日より前の日付は入力できない（422）
- [ ] 【M2】負の値は入力できない（422）
- [ ] 【M2】reviewer / demo による手入力は 403

### S8. ダッシュボード

**As a** 発信者
**I want** 企画の数字を1画面でざっと見たい
**So that** 毎日開いて、伸びているものに気づける

- [ ] 【M2】企画のダッシュボードで、**全チャネル横断の直近30日**の指標の推移を表示できる
- [ ] 【M2】**伸びている公開物 Top5**（直近の増加量で並べる。期間は design で決める）を表示できる
- [ ] 【M2】**ネタ在庫のサマリ**（状態別の件数）を表示できる
- [ ] 【M2】最後に取得が成功した日時と、直近の失敗の有無がダッシュボードで分かる
- [ ] 【M2】スナップショットが1件も無い企画でも、空の状態として崩れずに表示される
- [ ] 【M2】reviewer / demo も閲覧できる

### S9. 公開物ごとの推移

**As a** 発信者
**I want** 1本の記事の伸び方を見たい
**So that** 公開直後に伸びたのか、じわじわ伸びたのかが分かる

- [ ] 【M2】公開物ごとに、指標の**日次推移グラフ**を表示できる
- [ ] 【M2】欠測の日は、グラフ上で欠測と分かる（線をつながない、または印を付ける）
- [ ] 【M2】手入力の値は、自動取得の値と見分けられる
- [ ] 【M2】コンテンツの画面・公開済み一覧から、公開物の推移へたどれる

### S10. 分析

**As a** 発信者
**I want** 何が伸びて何が伸びなかったかを、条件を変えて比べたい
**So that** 次に書くものを決められる

- [ ] 【M2・統合時も残す】**公開後 N 日の伸びカーブ**を、公開日の違う公開物同士で比較できる（相対日数に正規化）
- [ ] 【M2・統合時も残す】**タグ別の反応**（平均・中央値）を比較できる
- [ ] 【M2・統合時も残す】**公開月ごとのコホート**で累積推移を見られる
- [ ] 【M2・統合時に落とせる】公開曜日別の反応を比較できる
- [ ] 【M2・統合時に落とせる】文字数帯別の反応を比較できる
- [ ] 【M2】分析はチャネルで絞り込める（チャネルによって指標の意味と桁が違うため、混ぜて平均しない）
- [ ] 【M2】集計は SQL（ウィンドウ関数・集約）で行い、アプリ側で全件を読み込んで計算しない

> 削る順番の1番目を発動した場合：分析画面は作らず、【統合時も残す】の3つをダッシュボードのパネルとして載せる。
> この3つは「日次スナップショットと時系列分析」（削ってはいけないもの）の担い手なので、統合しても落とさない。

### S11. 性能

**As a** 開発者
**I want** データが年単位で溜まっても画面が重くならないことを確かめたい
**So that** 「動く」だけでなく「溜まっても使える」と言える

- [ ] 【M2】インデックス設計と、日次の生データ／月次ロールアップの持ち分け、パーティショニングの要否を ADR-0008 に残す
- [ ] 【M3】**50万行のスナップショットをシードして実測する**（requirements-overview §6-1）
- [ ] 【M3】ダッシュボード初回表示 1秒以内、分析クエリ（タグ別・コホート）2秒以内を満たす
- [ ] 【M3】実測の Before/After（インデックス等の前後）を README に載せる
- [ ] 【M2】シードは本番の DB に入らない手順で投入する（開発・計測用）

### S12. テストと品質

- [ ] 【M2】Service 層のユニットテスト（認可分岐、同日上書き、手入力の検証、リトライの判定、RSS の重複判定、公開取消後の除外）
- [ ] 【M2】**Qiita API・RSS はテストで実際に呼ばない。** 差し替え可能な境界を置き、fake で成功・失敗・レート制限・タイムアウトを再現する
- [ ] 【M2】ワーカーのテスト：定期投入が二重にならない、リトライ上限で失敗が確定する、途中で落ちたジョブが回収される
- [ ] 【M2】分析クエリのテスト：小さな既知のデータで、伸びカーブ・タグ別・コホートの値が期待どおりになる（欠測を含む）
- [ ] 【M2】API の結合テスト（手動実行 → ワーカーを回す → スナップショット → ダッシュボード、および 401 / 403 / 404 / 409 / 422 の各系統）
- [ ] 【M2】新しい Service も HTTP に依存せず、MCP / ジョブから同じ認可で呼べる（`lint-imports` が緑）
- [ ] 【M2】`ruff` / `mypy` / `lint-imports` / フロントの `lint` / `tsc` / `build` が CI で緑
- [ ] 【M2】手動確認：**Qiita の公開物があり RSS を登録した企画で、1週間放置してスナップショットが溜まっている**（M2 の判定）。手動実行で進捗が流れる

## 6. 非機能・制約

- **依存方向**：`Controller → Service → Repository`（ADR-0009）。ジョブは Service を呼び、Repository を直接叩かない（structure.md）。commit の持ち主はワーカー（ADR-0017 と同じ）
- **認可**：本スペックで足すすべての操作を、Service 冒頭の明示チェックで判定する。SSE も例外にしない
- **ジョブ基盤**：PostgreSQL をキューにした自前ワーカー。Redis を入れない（ADR-0013）
- **外部 API の境界**：Qiita API・RSS の取得は差し替え可能な境界の向こうに置く。チャネルアダプタ（`app/channels/`）から呼ぶ
- **Qiita API**：取れる指標・レート制限は実装時に最新仕様で確かめる（requirements-overview §7）
- **時刻**：対象日は JST。DB には UTC の時刻で持ち、対象日は日付として別に持つ
- **フロント**：BFF 経由（ADR-0014）。SSE も BFF が中継し、ブラウザから FastAPI を直接叩かせない。グラフの描画ライブラリは design で選ぶ（ADR-0015 の方針に合わせる）
- **性能**：ダッシュボード 1秒以内、分析 2秒以内（requirements-overview §6-1）。M2 では設計、M3 で実測
- **コスト**：定期実行は1日1回。リトライは上限付きで、外部 API を叩き続けない

### 個人情報の扱い（グローバル CLAUDE.md §8）

| 観点 | このスペックでの扱い |
|---|---|
| 収集するもの | 公開物ごとの集計値（閲覧数・いいね等）だけ。**読者個人の情報（誰がいいねしたか等）は取らない** |
| 新しい秘密情報 | 無い。Qiita のトークンは publishing で登録したものを使う。RSS の URL は公開情報 |
| 第三者提供 | 無い（取得するだけで、外部へ送るものは無い） |
| 削除 | 公開物の取消後もスナップショットは残す。企画やユーザーの削除時の扱いは、削除機能を作るときに併せて決める |
| 最小化 | Qiita の API 応答のうち、指標以外（本文・コメントの中身等）は保存しない |
